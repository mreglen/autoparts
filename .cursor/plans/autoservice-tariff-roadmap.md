# Тариф «Автосервис» — мастер-план подключения, оплаты и разграничения доступа

> Статус документа: проектный дорожник для последовательной реализации.
>
> Этот файл описывает не один Build, а всю целевую систему. Каждый этап нужно
> отдельно уточнять в Plan mode и только затем реализовывать.

## Как пользоваться этим файлом

1. Приложи файл `.cursor/plans/autoservice-tariff-roadmap.md` в новый чат.
2. Включи **Plan mode**.
3. Напиши: `создай подробный план для этапа X из приложенного дорожника`.
4. Попроси агента сначала сверить этап с текущим кодом: предыдущие этапы могли уже изменить архитектуру.
5. Проверь подготовленный план и только после этого переходи в Build/Agent mode.
6. После реализации попроси:
   - прогнать релевантные тесты;
   - проверить миграции и обратную совместимость;
   - обновить журнал прогресса в конце этого файла.
7. Не объединяй несколько этапов в один Build без отдельного решения.

Рекомендуемый шаблон запроса:

```text

Создай подробный план для этапа X.
Перед планированием проверь текущее состояние репозитория и уже выполненные этапы.
Не реализуй код. Зафиксируй затрагиваемые файлы, API, миграции, тесты,
риски, обратную совместимость и критерии приёмки.
Если дорожник расходится с текущим кодом, укажи расхождение и предложи
минимально рискованное решение.
```

## 1. Цель продукта

На платформе должны сосуществовать:

- обычный покупатель;
- обычная организация;
- продавец запчастей;
- организация с подключённым тарифом «Автосервис».

«Автосервис» — это не новая роль пользователя и не отдельный аккаунт. Это
платная возможность организации.

Одна организация может одновременно:

- закупать запчасти;
- продавать свои запчасти;
- использовать модуль автосервиса;
- иметь сотрудников с аккаунтами;
- вести механиков без аккаунтов как исполнителей работ.

### Целевые коммерческие условия

- обычный покупатель: наценка Rossko **30%**;
- обычная организация: наценка Rossko **20%**;
- организация с действующим тарифом «Автосервис»: наценка Rossko **7%**;
- стоимость тарифа «Автосервис»: **10 000 ₽ в месяц**;
- оплата на первом этапе происходит вне сайта;
- администратор вручную фиксирует оплату на сайте;
- при окончании оплаченного периода льготная наценка прекращается;
- функции автосервиса приостанавливаются;
- организация продолжает работать как обычная организация с наценкой 20%;
- данные автосервиса не удаляются;
- после оплаты доступ и все прежние данные возвращаются.

Все проценты, стоимость, длительность теста и правила просрочки должны храниться
в настройках или тарифной модели, а не быть разбросаны hardcode-значениями по
frontend и backend.

## 2. Принципы, которые нельзя нарушать

### 2.1 Аккаунт пользователя не равен карточке сотрудника сервиса

Сохраняются две разные сущности:

1. **Пользователь организации** (`User`) — человек с логином, паролем и правами.
   Такие аккаунты нужны директору, приёмщику, закупщику и другим людям,
   которые работают на сайте.
2. **Сотрудник автосервиса** (`AutoserviceServiceEmployee`) — карточка механика
   или другого исполнителя без обязательной регистрации. Она нужна для
   назначения работ и расчёта зарплаты.

Не заставлять всех механиков регистрироваться. В будущем можно добавить
необязательную связь карточки механика с `User`, но нельзя делать её обязательной.

### 2.2 Тариф принадлежит организации

Статус тарифа, даты теста, оплаченный период и платежи привязаны к
`organization_id`, а не к директору или отдельному пользователю.

Смена директора не должна отключать тариф и не должна терять данные.

### 2.3 Приостановка — это ограничение доступа, а не удаление

При неоплате нельзя удалять:

- клиентов автосервиса;
- автомобили;
- записи;
- заказ-наряды;
- работы и запчасти;
- сотрудников автосервиса;
- начисления зарплаты;
- настройки, зоны и справочники;
- историю платежей и аудит.

### 2.4 Backend является источником истины

Скрытие меню на frontend не является защитой. Каждый backend endpoint
автосервиса должен проверять право организации на тариф.

### 2.5 Исторические цены неизменяемы

Изменение тарифной наценки применяется только к новым поискам, предложениям и
заказам. Сохранённые цены и `markup_percent` старых заказ-нарядов не
пересчитываются задним числом.

### 2.6 Заявка, подписка и оплата — разные сущности

- заявка отражает работу менеджера с потенциальным клиентом;
- подписка определяет доступ организации к функциям;
- платёж подтверждает деньги и продлевает оплаченный период.

Не объединять всё в одно поле `autoservice_status`.

## 3. Что есть в проекте сейчас

Перед каждым этапом агент обязан повторно проверить код. Этот раздел фиксирует
исходную точку на момент создания дорожника.

### Организации и роли

- `backend/app/models/organization.py` — организация и индивидуальная наценка
  новых запчастей.
- `backend/app/models/user.py` — роли `is_buyer`, `is_seller`, `is_admin`,
  `is_director`, `is_employee`.
- `frontend/my-autoparts/src/pages/Profile/EmployeesPage.jsx` — аккаунты
  сотрудников организации.
- `backend/app/models/autoservice_service_employee.py` — механики/исполнители
  без аккаунтов.

### Текущий автосервис

- `backend/app/models/autoservice_settings.py` — настройки автосервиса на
  организацию.
- `backend/app/utils/org_access.py` — `resolve_autoservice_organization_id()`
  выбирает первую организацию с пользователем `is_admin && is_director`.
- `backend/app/utils/autoservice_access.py` — backend-проверки доступа.
- `frontend/my-autoparts/src/utils/autoservicePublic.js` — frontend-проверки.
- `frontend/my-autoparts/src/App.js` — route guards.
- `frontend/my-autoparts/src/pages/Profile/menu/profileMenuConfig.js` — меню.
- `site_settings.show_autoservice` — глобальный флаг модуля.
- `/auth/public-site-config` отдаёт `show_autoservice` и один
  `autoservice_organization_id`.

Текущая архитектура фактически single-tenant: на сайте предполагается один
автосервис. Она не подходит для тарифа, подключаемого нескольким организациям.

### Наценки

Сейчас существуют минимум два независимых контура:

- наценка каталога новых запчастей:
  `backend/app/utils/org_markup.py`,
  `organizations.new_parts_markup_percent`,
  `organizations.new_parts_markup_manual`,
  `site_settings.new_parts_markup_percent`;
- наценка запчастей внутри заказ-наряда:
  `RepairOrderShopPart.markup_percent`, сейчас отдельно от тарифной наценки.

Перед изменением процентов агент должен найти полный путь цены Rossko:
backend-поиск → API-ответ → Redux/UI → корзина/заказ → сохранённая цена.
Нельзя считать, что изменение одного helper автоматически меняет всю цену.

### Ручные платежи

- `backend/app/models/site_payment.py`;
- `backend/app/routers/site_payments.py`;
- `frontend/my-autoparts/src/pages/Admin/SitePaymentsPage.jsx`;
- `SitePaymentLedger`.

Это полезный UX и технический образец, но текущие платежи сайта не привязаны к
организации и не должны смешиваться с оплатой тарифа автосервиса.

### Миграции

Проект использует:

- SQLAlchemy `Base.metadata.create_all`;
- idempotent `ensure_*` в `backend/app/db/schema_patches.py`;
- вызовы patch-функций в `backend/app/main.py`;
- `schema_patch_markers` для одноразовых преобразований.

Новые миграции должны следовать текущему стилю, пока проект отдельно не перейдёт
на Alembic. Запрещены destructive migration и повторное удаление данных.

## 4. Целевая предметная модель

### 4.1 Заявка на подключение

Рекомендуемая таблица: `autoservice_tariff_applications`.

Минимальные поля:

- `id`;
- `organization_id`;
- `applicant_user_id`;
- `contact_name`;
- `phone`;
- `email` (необязательно);
- `company_name_snapshot`;
- `comment`;
- `status`;
- `assigned_admin_id` (необязательно);
- `contacted_at`;
- `reviewed_at`;
- `rejection_reason`;
- `created_at`;
- `updated_at`.

Статусы заявки:

- `pending` — новая;
- `contacted` — менеджер связался;
- `approved` — принято решение подключить;
- `rejected` — отказ;
- `cancelled` — организация отозвала заявку.

Заявка после одобрения не удаляется. Она остаётся историей и связывается с
созданной подпиской.

Одна организация не должна создавать много активных заявок. Нужна серверная
защита от дублей для `pending/contacted`.

### 4.2 Подписка организации

Рекомендуемая таблица: `organization_autoservice_subscriptions`.

Минимальные поля:

- `id`;
- `organization_id` — unique FK;
- `status`;
- `trial_started_at`;
- `trial_ends_at`;
- `active_from`;
- `paid_until`;
- `grace_until` (если grace включён);
- `suspended_at`;
- `cancelled_at`;
- `monthly_amount`;
- `markup_percent`;
- `activated_by_id`;
- `suspension_reason`;
- `admin_notes`;
- `created_at`;
- `updated_at`;
- поле версии/optimistic locking желательно для защиты от одновременных действий.

Статусы подписки:

- `trial` — тестовый период;
- `active` — оплаченный период;
- `grace` — управляемая отсрочка после оплаты;
- `suspended` — доступ остановлен;
- `cancelled` — договорённость прекращена.

Для организации без строки подписки состояние считается `none`.

`pending`, `contacted`, `approved`, `rejected` не являются статусами подписки —
они принадлежат заявке.

### 4.3 Разрешение на функции (entitlement)

Нужно централизованное вычисление:

- `has_autoservice_access`;
- `has_autoservice_discount`;
- `is_autoservice_read_only`;
- `effective_autoservice_markup_percent`;
- `access_reason`;
- `expires_at`.

Рекомендуемая матрица:

- `none`: функций нет, наценка организации 20%;
- заявка `pending/contacted`: функций нет, наценка 20%;
- `trial`: полный доступ, наценка 7%, до `trial_ends_at`;
- `active`: полный доступ, наценка 7%, до `paid_until`;
- `grace`: политика настраиваемая; безопасный дефолт — доступ только для
  просмотра существующих данных, наценка уже 20%;
- `suspended`: функций нет, наценка 20%;
- `cancelled`: функций нет, наценка 20%.

Если бизнес решит давать в grace полный доступ и 7%, это меняется одной
политикой. Нельзя размазывать такое условие по endpoints.

Для MVP допустим `grace_days = 0`: на следующий момент после `paid_until`
подписка становится `suspended`. Это наиболее точно соответствует правилу
«не оплатили — стали обычной организацией».

### 4.4 Тестовый период

Рекомендуемый дефолт: 14 календарных дней, но значение должно настраиваться.

Правила:

- тест включает только администратор после разговора;
- тест запускается явным действием, не автоматически при отправке заявки;
- сохраняются начало, конец и кто включил;
- повторный тест нельзя включить случайно;
- повторный тест возможен только администратором с обязательной причиной;
- окончание теста без оплаты переводит подписку в `suspended`;
- платёж во время теста переводит подписку в `active`, не теряя данные.

### 4.5 Ручной платёж

Рекомендуется отдельная модель
`organization_subscription_payments` и ledger, а не переиспользование
`SitePayment` без разделения доменов.

Поля платежного периода:

- `id`;
- `organization_id`;
- `subscription_id`;
- `period_start`;
- `period_end`;
- `amount_due`;
- `amount_paid`;
- `status`: `draft`, `partially_paid`, `paid`, `cancelled`, `refunded`;
- `payment_method_note`;
- `invoice_reference`;
- `comment`;
- `recorded_by_id`;
- `created_at`;
- `updated_at`.

Ledger-запись:

- сумма;
- дата фактической оплаты;
- тип операции: `payment`, `correction`, `refund`;
- комментарий;
- администратор;
- время создания.

Правила:

- только администратор может отметить внешнюю оплату;
- запись платежа идемпотентна или защищена от случайного двойного нажатия;
- полная оплата продлевает `paid_until`;
- частичная оплата не активирует следующий период автоматически, если это
  отдельно не разрешено;
- ручная активация без полной оплаты требует причины и попадает в аудит;
- удалять платежи нельзя — только корректировать ledger-записью;
- денежные суммы хранятся в `Numeric/Decimal`, не `float`.

### 4.6 Аудит

Нужно журналировать:

- отправку и отзыв заявки;
- назначение ответственного;
- отметку «связались»;
- одобрение и отказ;
- запуск/продление теста;
- активацию, приостановку и отмену подписки;
- создание платежного периода;
- платеж, корректировку и возврат;
- ручное изменение дат и наценки;
- автоматическое окончание trial/active/grace.

Аудит должен содержать:

- администратора или системного инициатора;
- организацию;
- сущность и её id;
- старое и новое состояние;
- причину;
- дату.

## 5. Целевой клиентский сценарий

### 5.1 Где рассказать о тарифе

Основная точка — кабинет директора организации:

- карточка/настройки организации;
- отдельный блок «Тариф и возможности»;
- CTA «Подключить автосервис».

Дополнительные точки:

- страница тарифов;
- ненавязчивый баннер в закупках Rossko;
- расчёт примерной экономии при достаточном месячном объёме.

Тарифный текст:

> Тариф «Автосервис»: закупка запчастей с наценкой 7%, планировщик,
> заказ-наряды, клиенты, сотрудники и расчёт работ. Стоимость — 10 000 ₽
> в месяц. Оставьте заявку — мы свяжемся с вами и подключим тестовый или
> полный период.

Не обещать «экономию», пока расчёт не учитывает реальный объём и условия товара.

### 5.2 Что видит директор

- без заявки — описание и кнопка «Оставить заявку»;
- `pending` — «Заявка принята»;
- `contacted` — «Менеджер связался / подключение согласовывается»;
- `trial` — срок теста и оставшиеся дни;
- `active` — стоимость и «оплачено до»;
- перед окончанием — предупреждение;
- `grace` — условия отсрочки;
- `suspended` — «Доступ приостановлен, данные сохранены» и контакт для оплаты;
- `rejected` — нейтральный статус и контакт;
- `cancelled` — возможность подать новую заявку.

Обычный сотрудник организации не должен подавать заявку или видеть внутренние
финансовые комментарии. Он может видеть только понятный статус доступа.

### 5.3 Что видит администратор

Новый административный раздел «Тарифы автосервиса»:

- очередь новых заявок;
- фильтры по статусу и ответственному;
- контакты организации;
- история действий;
- кнопки «Связались», «Включить тест», «Активировать», «Отклонить»;
- оплачено до;
- ближайшие окончания;
- просроченные и приостановленные;
- действие «Отметить оплату»;
- ручная корректировка только с причиной.

### 5.4 Что происходит при неоплате

1. До окончания периода директор получает предупреждения.
2. После `paid_until` политика вычисляет отсутствие скидки.
3. Организация получает обычную наценку 20%.
4. Staff-функции автосервиса блокируются полностью или становятся read-only
   согласно выбранной политике.
5. Обычные функции организации и продавца продолжают работать.
6. Все данные автосервиса остаются в базе.
7. После фиксации оплаты подписка снова `active`.
8. Меню, endpoints и данные становятся доступны без ручного восстановления.

## 6. Целевая политика наценки

Наценку нужно вычислять в одном backend-сервисе. Frontend получает уже
разрешённую цену или тарифный контекст, но не решает право на 7%.

Целевая логика:

1. Определить покупателя и организацию из авторизованного контекста.
2. Если пользователь покупает как физлицо — 30%.
3. Если покупает от обычной организации — 20%.
4. Если покупает от организации с действующим entitlement тарифа — 7%.
5. При `suspended/cancelled/expired` — 20%.
6. Сохранить использованный процент и исходную цену в заказе/котировке.

Перед реализацией нужно отдельно решить:

- может ли директор переключать контекст «покупаю лично / от организации»;
- распространяется ли 7% на все предложения Rossko;
- входят ли доставка, комиссии, налоги и округление;
- действует ли 7% только в каталоге или также при добавлении Rossko в
  заказ-наряд;
- имеет ли индивидуальная договорная наценка приоритет над тарифом;
- что происходит с ценой в уже сформированной корзине при окончании тарифа.

Рекомендуемые безопасные дефолты:

- цена перепроверяется на backend при оформлении заказа;
- корзина не гарантирует старую льготную цену после окончания тарифа;
- заказ после создания хранит price snapshot и не пересчитывается;
- индивидуальный override разрешён только администратору, с датой и аудитом;
- наценка запчастей, которую сам автосервис выставляет своему клиенту внутри
  заказ-наряда, не равна закупочной тарифной наценке 7%.

Последний пункт принципиален:

- **7%** — сколько платформа добавляет к закупочной цене для организации;
- `RepairOrderShopPart.markup_percent` — сколько автосервис добавляет своему
  клиенту при продаже детали.

Эти проценты нельзя хранить в одном поле.

## 7. Целевая архитектура доступа

### Global master switch

`site_settings.show_autoservice` можно сохранить как аварийный/глобальный
переключатель модуля. Он не определяет, какая организация оплатила тариф.

### Organization entitlement

Нужны backend helpers примерно такого назначения:

- получить подписку организации;
- вычислить entitlement на текущий момент;
- потребовать staff-доступ;
- потребовать director-доступ;
- потребовать write-доступ;
- вернуть тарифный контекст для цены.

Каждый staff endpoint должен использовать текущего пользователя и
`user.organization_id`, а не глобальный `autoservice_organization_id`.

### Frontend

Профиль пользователя/API `me` должен отдавать компактный безопасный контекст:

- `autoservice_status`;
- `autoservice_access`;
- `autoservice_read_only`;
- `autoservice_trial_ends_at`;
- `autoservice_paid_until`;
- `can_manage_autoservice_subscription`.

Frontend использует его для меню и баннеров. Backend повторно проверяет доступ.

### Публичная часть и несколько автосервисов

Текущий публичный `/autoservice` рассчитан на одну организацию. Подключение
тарифа нескольким организациям создаёт отдельное продуктовое решение:

- каталог автосервисов;
- URL `/autoservices/:slug` или `/autoservices/:organizationId`;
- выбор сервиса клиентом;
- публичные настройки и запись в конкретную организацию.

Это не должно блокировать внутренний тарифный MVP. До отдельного этапа:

- существующий публичный автосервис остаётся primary/legacy;
- новые организации получают staff-функции и закупочную наценку;
- публичная публикация нового автосервиса включается отдельно;
- нельзя автоматически направлять всех клиентов к последней подключённой org.

`0 → 1 → 2 → 3 → 4 → 5`

После backend API можно параллельно планировать:

- этап 6 — кабинет организации;
- этап 7 — админский интерфейс.

Доступ и UI:

`2 + 5 + backfill → 8 → 9`

Цены:

`0 + 2 + 8 → 10`

Автоматизация:

`2 + 5 + 8 + 10 → 11`

Проверка сохранности:

`8 + 9 + 10 + 11 → 12`

`8 + 9 → 13`, но этап можно отложить после MVP.

Онлайн-оплата:

`5 + стабильный ручной процесс → 14`.

## 10. Backfill существующего автосервиса

До переключения guards нужно:

1. Найти текущую org через legacy
   `resolve_autoservice_organization_id()`.
2. Создать ей подписку.
3. Не пытаться автоматически считать `paid_until` из `SitePayment`: это другой
   вид платежей без надёжной связи с org.
4. На первом rollout безопаснее поставить:
   - `status=active`;
   - ограниченный временный `paid_until`, согласованный администратором; или
   - legacy entitlement до ручного завершения миграции.
5. Зафиксировать backfill marker.
6. Проверить количество клиентов, авто, заказов, сотрудников и настроек до/после.
7. Только после проверки включать новые access guards.
8. Legacy resolver оставить как временный fallback на один релиз, затем удалить.

Backfill не должен:

- пересчитывать исторические цены;
- менять `RepairOrderShopPart.markup_percent`;
- менять статусы заказов;
- удалять клиентов;
- повторно запускать старые destructive patches.

## 12. Общая матрица безопасности

Каждый этап API должен проверить:

- пользователь авторизован;
- пользователь принадлежит нужной организации;
- управляющее действие выполняет директор или platform admin;
- обычный employee не видит платежи и admin notes;
- staff org A не получает данные org B;
- подмена `organization_id` в URL/body не меняет scope;
- suspended org не обходит guard прямым URL/API;
- frontend cache не сохраняет доступ после expiry;
- admin override требует причины;
- payment endpoint защищён от повторов;
- audit не содержит пароли и чувствительные платёжные данные.

## 13. Общая стратегия тестирования

### Backend unit

- state machine;
- entitlement по времени;
- pricing policy;
- расчёт периодов;
- Decimal и округление;
- допустимые роли.

### Backend integration

- заявка → trial;
- заявка → оплата → active;
- active → expired/suspended;
- suspended → payment → active;
- isolation двух организаций;
- сохранность данных;
- scheduler idempotency;
- audit.

### Frontend

- отображение CTA и статусов;
- menu guards;
- route guards;
- admin forms;
- повторная отправка;
- mobile/responsive;
- refresh после изменения статуса.

### E2E business scenarios

1. Обычная org с 20% подаёт заявку.
2. Админ звонит и включает 14 дней.
3. Org получает 7% и функции.
4. Тест заканчивается без оплаты.
5. Org возвращается к 20%, данные сохранены.
6. Админ отмечает 10 000 ₽.
7. Org снова получает 7% и прежнее рабочее пространство.
8. Другая org не видит эти данные.

## 14. Rollout и наблюдаемость

Рекомендуемый rollout:

1. deploy схем без изменения поведения;
2. deploy API и admin-only управление;
3. backfill текущей org;
4. проверить audit и entitlement в shadow/dry-run;
5. включить новые backend guards;
6. включить frontend кабинет;
7. включить pricing policy ограниченной группе;
8. проверить реальные цены Rossko;
9. включить scheduler;
10. открыть заявки всем директорам организаций.

Нужные метрики/логи:

- количество заявок по статусу;
- active/trial/ending/suspended;
- ошибки переходов;
- denied access по причине;
- платежи и задолженность;
- scheduler processed/failed;
- расхождение сохранённого status и вычисленного entitlement;
- pricing policy branch: retail/org/autoservice;
- число reactivation после оплаты.

## 15. Definition of Done для каждого этапа

Этап не завершён, пока:

- план сверён с актуальным кодом;
- миграции idempotent;
- нет удаления production-данных;
- backend permission checks реализованы;
- frontend не является единственной защитой;
- audit добавлен для значимых действий;
- тесты этапа проходят;
- существующий автосервис не сломан;
- обычные покупатели, организации и продавцы не получили регрессию;
- lint/diagnostics проверены;
- документация API/статусов обновлена;
- журнал прогресса заполнен;
- deploy не выполнялся без отдельной просьбы.

## 16. Решения, которые нельзя принимать «заодно»

Следующие темы требуют отдельного подтверждения:

- изменение 30/20/7;
- бесплатный grace;
- доступ read-only;
- автоматический повторный trial;
- индивидуальная скидка;
- публикация организации как СТО;
- перерасчёт старой корзины;
- изменение розничной наценки заказ-наряда;
- создание аккаунтов всем механикам;
- удаление данных после отмены;
- онлайн-списание денег;
- объединение платежей сайта и тарифа автосервиса.

Если решение не принято, агент должен использовать безопасный дефолт из этого
дорожника и явно указать его в плане этапа.
