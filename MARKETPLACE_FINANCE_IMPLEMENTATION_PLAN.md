# План развития: единый учёт, маркетплейс Б/У, Авито, финансы

Все учётные решения только **внутри платформы** (без интеграций с 1С и прочими внешними ERP).

**Как работать по этому документу:** выберите один **этап** → включите режим Plan в Cursor, приложите этот файл (или нужный раздел этапа) → после согласования плана включите Agent mode для реализации. Не смешивайте этапы в одном PR без необходимости.

---

## Ключевые договорённости

| Тема | Решение |
|------|---------|
| Факт расхода/продажи со склада | Запись `stock_out` + уменьшение `products.quantity` |
| Маркетплейс (этапы 2–3) | **Только Б/У** заказы (`garage_used_orders`). Новые заказы гаража вне этого плана или как фоновые задачи |
| Корзина с товарами разных продавцов | **Один заказ = одна организация-продавец**. Корзину **разносим по нескольким `GarageUsedOrder`** (покупатель получает несколько номеров заказов или один «групповой номер группы заказов» — по ТЗ после этапа 2.1) |
| Цена продажи в склад | Брать из строки заказа или из карточки — зафиксировать в задаче этапа 2 |

---

## Этап 1 — Единый контур продажи и склада

**Цель:** одна техническая дорожка создания складского расхода/продажи из всех источников (ручная продажа, Авито, маркетплейс Б/У): идемпотентность, явный **источник** операции.

### Задачи

1. Спроектировать поля связи `stock_out` ↔ источник (например: `source_kind` enum + FK на позицию заказа маркетплейса / уже есть `avito_order_id` + `sale_channel`).
2. Вынести в сервис (например `app/services/stock_sale_fulfillment.py`) метод вроде `create_sale_stock_out(...)`: проверка остатка, создание строки, `commit`, анти-дубликат по ключу источника.
3. Перевести **Avito closed** на вызов этого сервиса (тонкая обёртка над текущим `avito_closed_order_processor`).
4. Перевести **ручную продажу** `POST /stock-outs/` на тот же путь или оставить вызовом сервиса с `source_kind=warehouse_manual` (решение в рамках этапа).
5. Обновить/дополнить юнит-тесты сервиса (хотя бы идемпотентность и обрезание qty).

### Критерии приёмки

- Повторный вызов с тем же источником не создаёт второй `stock_out`.
- В API/админке видно канал и привязку к источнику (или в модели есть поля под это).

### Точки входа в коде (ориентир)

- [`backend/app/routers/stock_outs.py`](backend/app/routers/stock_outs.py)
- [`backend/app/services/avito_closed_order_processor.py`](backend/app/services/avito_closed_order_processor.py)
- [`backend/app/models/stock_out.py`](backend/app/models/stock_out.py)

### Зависимости

Нет (первый этап).

## Этап 2 — Маркетплейс: оформление Б/У и разнесение заказов по продавцам

**Цель:** корректное создание заказов с сайта: **товары из корзины группируются по `products.organization_id`**, создаётся **несколько** `GarageUsedOrder`, у каждого — своя сумма и свои строки; покупатель и доставка — общие поля во все заказы.

### Задачи

1. **Бэкенд `POST /orders/`** ([`backend/app/routers/orders_legacy.py`](backend/app/routers/orders_legacy.py)):
   - Для режима только Б/У: брать элементы корзины/пэйлоада, резолвить `organization_id` продавца по каждому `product_id`.
   - Сгруппировать по `seller_organization_id`; для **каждой группы** создать отдельный `GarageUsedOrder` с `organization_id=<организация продавца>`.
   - `total_amount` пересчитать **на заказ**, не общий суммой корзины.
   - Ответ API: например `{ "orders": [{ "id", "organization_id", "total_amount" }, ...] }` (сохранить обратную совместимость с фронтом или обновить фронт синхронно).

2. **Покупатель:** убедиться, что авторизация позволяет оформлять заказ **без принадлежности к организации продавца** (`current_user.organization_id` сейчас используется как продавец — это блокер маркетплейса; потребуются правила: организация в заказе = продавец, покупатель = поля buyer_*).

3. **Фронт [`OrderRegistration.jsx`](frontend/my-autoparts/src/pages/Cart/OrderRegistration.jsx)** (и Redux корзину):
   - Отправить данные так, чтобы бэкенд мог сгруппировать (список `items` с `product_id`, ids корзины — по желанию).
   - После успеха: показать несколько номеров заказов или сводку «Создано N заказов» + ссылки «Мои покупки».

4. Валидация остатка **до сохранения** заказов (опционально на этом этапе; обязательно до списания в этапе 3 по статусам).

### Критерии приёмки

- Корзина: 2 запчасти от продавца A и 1 от B → после оформления **2 записи** в `garage_used_orders`, разные `organization_id`.
- Никакая организация не получает заказ чужих позиций.

### Зависимости

Рекомендуется после **Этапа 1**, но можно параллелить точечно; **Этап 3** точно нужен связки со складом.

## Этап 3 — Списание со склада при жизненном цикле заказа маркетплейса (Б/У)

**Цель:** при переходе заказа (или каждого заказа в группе) в зафиксированный статус выполнить **однократное** списание через сервис этапа 1.

### Задачи

1. Выбрать триггер (зафиксировать в задаче и в этом файле после ревью), например: статус **`assembled`** или **`confirmed`**.
2. В `PUT /sales/used-parts-orders/{id}/status` или в отдельном хендлере «Подтвердить отгрузку» вызвать сервис для **каждой строки** с `product_id`:
   - `sale_price` из строки заказа или из карточки (как решите в начале этапа),
   - `sale_channel` / `source_kind` = маркетплейс Б/У,
   - привязка к `GarageUsedOrderItem.id`.
3. На позиции заказа: поле **`stock_out_id`** или **`fulfilled_at`** (исключить повторное списание).
4. Обработать отмену до триггера / после (возврат через существующий механизм `stock_out returns` где применимо).

### Критерии приёмки

- После триггерного статуса: `products.quantity` уменьшился; в `/stock-out` видна связь с заказом/каналом.
- Повторная смена статуса не дублирует списание.

### Зависимости

**Этап 1** и **Этап 2** выполнены (или хотя бы 2 с корректным `organization_id` продавца).

## Этап 4 — Отладка и стабилизация Авито

**Цель:** синк заказов, `closed` → склад без ошибок сумм и без двойных `stock_out`.

### Задачи

1. Пропустить создание через **единый сервис этапа 1** (если ещё не сделано полностью).
2. Алерты/логи по причинам skip (нет линка, недостаток qty, странный payload цены).
3. UI-хинт продавцу: «заказ закрыт на Авито, склад не проведён» при рассогласовании.
4. Регрессия на скрипт пересчёта цен и повторном sync.

### Критерии приёмки

- Чек-лист ручной на 10+ закрытых заказов сравнивает суммы Avito ↔ `stock_out`.
- Нет дублей при повторном запуске sync.

### Зависимости

**Этап 1** (желательно завершён).

## Этап 5 — Страница «Финансы»: отчёты и экспорт XLSX

**Цель:** одна страница в ЛК продавца/админа с отчётами **только по данным платформы**, выгрузка **.xlsx**.

### Задачи

1. **Бэкенд** — роутер, например `GET /finance/...`:
   - Продажи за период (строки из `stock_out` с фильтром по организации пользователя и датам),
   - Списания,
   - Поступления (`stock_in`),
   - При необходимости срез остатков на дату.
2. **`GET или POST .../export.xlsx`** с теми же фильтрами (библиотека `openpyxl` или `xlsxwriter` в зависимостях проекта).
3. **Фронт** — маршрут `/finance` или подраздел продаж:
   - Фильтры даты,
   - Табличный предпросмотр,
   - Кнопка «Скачать XLSX».
4. Права: permission `finance.reports` или только `seller`/`admin`.

### Критерии приёмки

- Числа в UI совпадают с `/warehouse-sales` и суммарной логикой за тот же период при одинаковых фильтрах.
- Файл открывается в Excel/Google Sheets без ошибки кодировки.

### Зависимости

**Этап 1** и корректные **каналы/источники** в `stock_out` упрощают группировки «по Авито / сайту / складу».

## Этап 6 — Регрессия, документация оператора

**Цель:** снять риски перед продом.

### Задачи

1. Пройти сценарии: несколько продавцов в корзине → несколько заказов → несколько списаний.
2. Краткая внутренняя инструкция: что такое статус триггера, где смотреть финансы, что делать при отмене.
3. Минимальные автотесты API для `POST /orders/` (split по орг).

### Зависимости

Этапы 1–5.

## Общая схема зависимостей

```
Этап 1 (единый сервис stock_out / источник)
    │
    ├──► Этап 4 (Авито через сервис)
    │
    ├──► Этап 3 (списание по статусу Б/У)
    │
    └──► Этап 5 (финотчёты по каналам)

Этап 2 (разнесение заказов по организациям) ──► Этап 3

Этап 6 (после 1–5)
```

## Ориентировочные сроки (1 разработчик)

| Этап | Единица | Приблизительно |
|------|---------|----------------|
| 1 | Единый контур | 1–2 недели |
| 2 | Разнесение заказов + покупатель/организация | 1,5–2,5 недели |
| 3 | Списание по статусу | 1–2 недели |
| 4 | Авито | 1–2 недели |
| 5 | Финансы + XLSX | 2–3 недели |
| 6 | Регрессия + документы | 3–7 дней |

**Итого:** порядка **8–11 недель** при последовательной работе приоритетным порядком: **1 → 2 → 3**, параллельно где возможно **4 после 1**, **5 можно начинать после стабильных каналов в БД**.

## Замечание про текущий `POST /orders/`

Файл [`backend/app/routers/orders_legacy.py`](backend/app/routers/orders_legacy.py) сейчас подставляет `organization_id` из **`current_user`** — это соответствует сценарию «продавец оформляет себе», а не «покупатель покупает у разных продавцов». **Этап 2 обязан** перевести `organization_id` заказа на **организацию продавца** для Б/У и поддержать **разделение покупателя** (поля получателя уже есть).
