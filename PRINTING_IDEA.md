# Печать этикеток/чеков “с любого устройства через сервер и ПК-агент”

## 1) Идея (что вы хотите получить)
Вы хотите сделать систему, где:
- Пользователь на любом устройстве открывает страницу (например, `/my-parts`).
- Нажимает “Печать”.
- Выбранный принтер и данные печати отправляются на ваш сервер.
- Сервер передает команду на ПК, к которому “привязан” этот принтер (через вебсокет).
- ПК на месте формирует/отправляет команду в драйвер и печатает.
- Печать происходит по заранее заданному шаблону (HTML-шаблон этикетки или чек).

Также вы хотите подключать ПК-агент через токен: “человек скачал программу → подключил токен → всё работает”.

## 2) Реалистично ли так сделать?
Да, такую архитектуру сделать можно, и она является распространенной для удаленной печати:
1. **Центральный сервер** принимает запросы на печать и управляет очередями/статусами.
2. **Локальный агент на ПК** подключается к серверу по токену и берет команды в печать.
3. **Сервер маршрутизирует запрос**: “кому отправить” (какой ПК/агент и какой принтер).

Ключевой момент: локальный агент должен уметь **в нужном формате** печатать контент (текст, штрихкоды, этикетки с фиксированной разметкой, возможно ESC/POS для чековых принтеров).

## 3) Что необходимо для реализации (по компонентам)

### 3.1. Локальный ПК-агент
Что должно быть в агенте:
- **Подключение к серверу по вебсокету**.
- **Аутентификация токеном** (проверка “этот агент от организации N”).
- **Получение списка доступных принтеров на ПК** (локальное перечисление принтеров).
- **Выбор целевого принтера** по имени/ID.
- **Получение задач печати** (job) от сервера.
- **Печать**:
  - для чеков/текста: агент отправляет “готовый” текст в драйвер (или работает через GDI/RAW).
  - для HTML-шаблонов: обязательно нужна стадия “рендеринга” шаблона в печатный формат (см. ниже).
- **Отчет о статусе печати** обратно на сервер (pending/printing/success/error) по `job_id`.

Важно: агент, который печатает “контент строкой”, не сможет “прямо” распечатать HTML. Нужно либо:
- преобразовать HTML в печатный формат, либо
- сменить стратегию формирования печати (например, генерировать текст/ESC-команды на сервере).

### 3.2. Сервер (backend)
Что должен делать сервер:
- **API для создания печатной задачи** (endpoint, который `/my-parts` дергает при нажатии “Печать”).
- **Валидация прав** (кто может печатать в какую организацию).
- **Создание job_id**, хранение статуса и данных печати.
- **Маршрутизация**:
  - найти активный агент для нужной организации,
  - убедиться, что нужный принтер существует у этого агента.
- **Отправка print-команды** на агент по вебсокету.
- **Получение статуса** от агента и обновление job в очереди.
- **Эндпоинт получения jobs** для UI (чтобы на странице виден статус).

### 3.3. Веб-интерфейс (`/my-parts`)
Что должно быть в UI:
- Страница “Печать” должна:
  - запрашивать доступные принтеры,
  - показывать пользователю список принтеров,
  - позволять выбрать принтер,
  - отправлять на сервер: `{printer, template/data, copies, ...}`.
- После отправки:
  - UI может обновлять очередь печати (по polling/websocket/interval).

### 3.4. Шаблоны (ваша HTML-этикетка)
Вы уже сделали HTML-шаблон с полями:
- бренд
- артикул
- внутренний код
- адресное хранение

Но чтобы **реально распечатать**, нужно определиться, как вы превращаете HTML в то, что сможет напечатать агент:

Варианты (без кода, концептуально):
1. **Рендерить HTML в картинку (PNG) или PDF**, затем печатать как изображение:
   - плюс: сохраняется визуальная верстка;
   - минус: зависит от того, как агент/ОС печатает изображения, и как драйвер воспринимает такие данные.
2. **Рендерить HTML на сервере/агенте в фиксированный “печатный текст”** (строки + переносы + моноширинный шрифт):
   - плюс: проще для многих принтеров чекового формата;
   - минус: сложнее повторить точную верстку HTML.
3. **Сгенерировать ESC/POS (или другой язык принтера) на основе данных**, а не HTML:
   - плюс: для чековых принтеров часто самый надежный путь;
   - минус: требует знания конкретного языка/капаций принтера.

Сейчас у вас агент логически печатает “контент как строку” (текст/RAW/TEXT/GDI). Поэтому для HTML-этикеток минимально нужно добавить “шаг превращения шаблона в печатный формат”.

## 4) Ответ на вопрос про Wi‑Fi принтер
Если ваш принтер — Wi‑Fi и вы подключили его **к одному ПК**:
- На ПК установлены драйверы (или включена поддержка сетевой печати).
- И агент печатает на этот принтер через драйвер Windows.

Тогда да: **через этот ПК вы сможете печатать с других устройств**, потому что:
- другие устройства передают задачу на сервер,
- сервер передает ее на ПК-агент,
- ПК-агент печатает “локально” на принтер, как если бы печатали прямо с этого ПК.

Ограничение:
- Wi‑Fi принтер в сети “как устройство” не обязан поддерживать печать напрямую с телефона/ноутбука. Ему важен факт печати со стороны ПК, к которому он подключен.
- Если принтер “сломает” отправку определенным способом (например, для RAW/TEXT нужны ESC/POS), придется подбирать правильный путь печати (и он может отличаться от принтера к принтеру).

## 5) Риски/ограничения, о которых лучше знать заранее
- **Надежность печати зависит от драйвера** и типа принтера (чековый, этикеточный, лазерный, термопринтер и т.п.).
- **HTML “не равен печати”**: HTML надо преобразовать в то, что понимает печатный путь.
- **Оффлайн агент**: если ПК выключен/агент не подключился, печать не произойдет (и это нужно красиво отрабатывать в UI).
- **Очереди и повторы**: при ошибках нужно решать, повторять ли job автоматически.
- **Безопасность токенов**: токен должен храниться и передаваться безопасно, иначе любой с токеном сможет печатать в вашу организацию.

## 6) Короткий вывод
Так сделать можно: сервер + токен-аутентифицированный вебсокет-агент на ПК + печать на локальные принтеры через драйвер.
Для печати по HTML-шаблону нужна дополнительная стадия рендеринга (HTML -> печатный формат).

## 7) Что уточнить, чтобы выбрать правильный путь печати
1. Тип принтера: это чековый термопринтер или этикеточный (и какая модель)?
2. Принтер поддерживает ESC/POS? Если да — какой формат (кодировки, команды)?
3. Нужен ли штрихкод/QR (кроме текста)?
4. Вы хотите печатать “строго по макету этикетки” (pixel-perfect) или допустимы компромиссы по верстке?

## 8) Пошаговые шаги разработки (подключение и настройка печати)
Ниже только архитектура и “склейка” компонентов: сервер <-> агент <-> UI. Процесс рендеринга/печати и состав полей этикетки намеренно не описываю.

### Шаг 1. Зафиксировать “контракт” печати (данные и жизненный цикл)
1. Определите сущности и статусы:
   - `Printer` (что мы считаем “одним принтером” на ПК: имя/ID, который возвращает агент)
   - `PrintJob` (job_id, printer_id, status: `pending/printing/success/error`, timestamps)
2. Зафиксируйте форматы сообщений:
   - сообщения, которые UI отправляет на сервер (endpoint, payload)
   - сообщения, которые сервер отправляет агенту по WebSocket (job данные + job_id + выбранный принтер)
   - сообщения, которые агент отправляет обратно серверу (обновление статуса по job_id)
3. Определите единый способ выбора принтера:
   - как из UI-поля “выбран принтер” получается `printer_id` для сервера (например `agent_hostname + локальное имя принтера`).

### Шаг 2. Базовые endpoint’ы и авторизация на сервере
1. Реализуйте API управления токенами агента (если еще нет):
   - генерация `printer_token` для организации
   - получение “текущего токена” с маскированием
2. Реализуйте API для UI:
   - получение списка принтеров, доступных организации пользователя (агенты + принтеры с активных ПК)
   - создание `PrintJob` по нажатию “Печать”
   - получение статуса/очереди `PrintJob` (чтобы UI мог показать прогресс)
3. Реализуйте WebSocket обработку:
   - handshake: проверка `X-Printer-Token` и `X-Organization-ID`
   - обработка сообщений “регистрация принтеров” и “job status update”
4. Добавьте контроль прав:
   - пользователь может печатать только в рамках своей организации
   - агент не должен “привязываться” к чужой организации.

### Шаг 3. Локальный агент: установка связки “ПК <-> сервер”
1. Подготовьте способ конфигурации агента:
   - способ получения `printer_token` и `organization_id` (CLI аргументы, конфиг, UI-форма)
2. Реализуйте запуск/жизненный цикл:
   - агент стартует, подключается к WebSocket
   - при успешном подключении регистрирует себя: `hostname` + список принтеров
3. Реализуйте “живучесть”:
   - реконнект при потере сети
   - периодический heartbeat (ping/pong) для быстрой детекции разрыва.
4. Реализуйте сопоставление принтера:
   - агент должен возвращать список принтеров в формате, который сервер сможет использовать для routing.

### Шаг 4. Роутинг заданий “сервер -> нужный ПК -> нужный принтер”
1. При создании `PrintJob` сервер:
   - определяет, какой агент/ПК обслуживает `printer_id`
   - проверяет, что агент подключен (есть WebSocket)
   - отправляет команду агенту с `job_id` и параметрами задачи (copies + content payload).
2. Сервер обновляет `PrintJob` статусы:
   - ставит `printing` при отправке команды
   - переводит `success/error` по отчету агента.
3. Обработайте ситуации:
   - агент отключился между созданием job и отправкой
   - выбранный принтер пропал/переименован
   - дубликаты (повтор запросов с фронта).

### Шаг 5. UI: интеграция со страницей `/my-parts`
1. Согласуйте поведение кнопки “Печать”:
   - при открытии страницы: подгрузить список доступных принтеров для текущего пользователя
   - при выборе принтера: подготовить payload для сервера
2. Согласуйте UX по очереди:
   - UI показывает job_id и статус (pending/printing/success/error)
   - UI умеет обновлять статус (polling или подписка, если вы добавите).
3. Привяжите авторизацию:
   - UI должен передавать идентичность пользователя так, чтобы сервер корректно определил организацию.

### Шаг 6. Сетевые/производственные настройки
1. Домен и доступность WebSocket:
   - настройте reverse proxy (например Nginx) так, чтобы WebSocket работал стабильно
2. HTTPS и CORS (если есть отдельный фронтенд домен):
   - убедитесь, что запросы из браузера разрешены
3. Переменные окружения:
   - адрес WebSocket/серверного API
   - секреты/токены (если нужны) и параметры подключения к БД.

### Шаг 7. Надежность и безопасность (обязательно)
1. Токен агента:
   - токен нельзя светить в логах
   - токен должен использоваться только для соединения агента и маршрутизации.
2. Rate limits и защита от повторов:
   - ограничить создание job’ов, чтобы один пользователь не “забил” очередь
3. Идемпотентность:
   - если UI повторно отправит запрос (плохая сеть), желательно избежать печати дублей (на уровне job-идемпотентности).
4. Обработка ошибок:
   - понятные статусы в UI
   - корректное завершение job при падении агента.

### Шаг 8. План тестирования (интеграционный)
1. Юнит-тесты логики сервера:
   - права доступа по организации
   - создание job и правильный выбор routing
2. Интеграция:
   - сервер + один локальный агент + выбор принтера
3. Сценарии с сетью:
   - агент теряет соединение во время печати (что показывает UI)
4. Тест “удаленное устройство”:
   - с другого ПК/телефона отправить job на сервер и убедиться, что он ушел на тот же ПК-агент.
