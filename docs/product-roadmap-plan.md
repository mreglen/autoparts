# План развития сайта «Свой Гараж»

Этот документ нужен как рабочий план для поэтапной разработки. Его можно прикреплять в Cursor в **Plan mode**, писать «этап 1», «этап 2» и так далее, затем после согласования нажимать **Build**.

Главное правило: перед реализацией каждого этапа агент в Plan mode должен задать уточняющие вопросы, согласовать границы этапа и только потом предлагать конкретный план изменений.

## Как пользоваться этим планом

1. Открыть новый чат или продолжить текущий.
2. Переключиться в **Plan mode**.
3. Прикрепить этот файл: `docs/product-roadmap-plan.md`.
4. Написать, например: `этап 1`.
5. Агент должен:
   - прочитать описание этапа;
   - изучить связанные файлы проекта;
   - задать уточняющие вопросы;
   - предложить план реализации;
   - дождаться подтверждения.
6. После согласования нажать **Build**, чтобы агент начал реализацию.

## Обязательные правила для всех этапов

- Не делать сразу несколько больших этапов за один Build.
- Не менять архитектуру шире, чем требует текущий этап.
- Не удалять старое поведение без проверки, используется ли оно в маршрутах, Redux, API или на сервере.
- После каждого этапа проверять линтеры и запускать доступные тесты/сборку, если это разумно.
- Если этап затрагивает продакшен-поведение, в конце писать короткий deploy checklist.
- Для каждого этапа в Plan mode обязательно задавать уточняющие вопросы.
- Если в этапе есть уведомления, делать их только:
  - в PWA-приложении;
  - на email.
- Пока не планировать SMS, Telegram, WhatsApp, push через сторонние мобильные SDK или внешние мессенджеры.
- Все новые пользовательские тексты писать простым русским языком.
- В интерфейсе не оставлять заглушки «в разработке», если раздел доступен пользователю.

## Приоритеты

### Высокий приоритет

- Убрать недоделанные или вводящие в заблуждение места.
- Довести покупку б/у запчастей до понятного пути.
- Сделать кабинет продавца более полезным каждый день.
- Почистить старый код заказов и навигационные несоответствия.
- Довести SEO и микроразметку до стабильного состояния.

### Средний приоритет

- Улучшить аналитику продавца.
- Доделать Drom, если он действительно нужен как канал продаж.
- Добавить PWA/email-уведомления.
- Усилить доверие к продавцам и карточкам товаров.

### Низкий приоритет

- Новые маркетплейсы помимо Avito/Drom.
- Большие переписывания архитектуры.
- Сложные внешние коммуникации: SMS, Telegram, WhatsApp.
- Новые разделы, если текущие разделы с заказами, возвратами и интеграциями остаются недоделанными.

# Этап 1. Убрать заглушки и недоделанные пользовательские разделы

## Цель

Сделать так, чтобы пользователь не попадал в разделы, где написано «функционал находится в разработке», если раздел нельзя использовать.

## Почему важно

Заглушки снижают доверие. Лучше скрыть раздел или показать честное состояние там, где оно действительно нужно, чем давать пользователю пустой экран.

## Что входит

- Найти все видимые пользователю заглушки.
- Решить для каждой:
  - скрыть из меню;
  - заменить на рабочий MVP;
  - оставить только для админа/разработчика;
  - объединить с существующей рабочей страницей.
- Проверить разделы возвратов.
- Проверить Rossko-заказы.
- Проверить старые страницы заказов, если они не используются.

## Известные места

- `frontend/my-autoparts/src/pages/Sales/SalesReturnsPage.jsx`
- `frontend/my-autoparts/src/pages/Sales/PurchasesReturnsPage.jsx`
- `frontend/my-autoparts/src/pages/Sales/PurchasesReturnsTab.jsx`
- `frontend/my-autoparts/src/pages/Sales/ReturnsTab.jsx`
- `frontend/my-autoparts/src/pages/Sales/RosskoOrdersTab.jsx`
- `frontend/my-autoparts/src/config/profileMenuConfig.js`
- `frontend/my-autoparts/src/App.js`

## Возможный подход

### Вариант A. Скрыть недоделанное

Подходит, если раздел пока не нужен пользователям.

Плюсы:
- быстро;
- меньше риска;
- интерфейс становится чище.

Минусы:
- функциональность не появляется;
- позже нужно не забыть вернуть разделы.

### Вариант B. Сделать MVP

Подходит, если раздел уже нужен в работе.

Плюсы:
- пользователь получает полезную функцию;
- меньше пустых обещаний.

Минусы:
- больше времени;
- нужно продумать статусы, API, права.

## Уточняющие вопросы в Plan mode

- Возвраты сейчас реально нужны продавцам или покупателям?
- Лучше временно скрыть возвраты или сделать простой MVP?
- Rossko-заказы нужны продавцу в кабинете или только админу?
- Какие пункты меню можно убрать без вреда?
- Нужно ли показывать «скоро появится» только админу?

## Результат этапа

- В пользовательском интерфейсе нет бесполезных заглушек.
- Меню соответствует реально работающим маршрутам.
- Пользователь не видит пустые разделы.

## Критерии готовности

- Поиск по коду не находит пользовательских заглушек «в разработке» в доступных разделах.
- Все пункты меню ведут на рабочие страницы.
- Линтер без новых ошибок.

# Этап 2. Настройка режима покупки б/у запчастей

## Цель

Подключить уже существующую настройку `used_parts_purchase_mode` к интерфейсу и поведению карточки б/у товара.

## Почему важно

Покупателю должно быть понятно, что делать:

- купить через корзину;
- написать продавцу;
- выбрать один из двух вариантов.

Сейчас настройка частично есть в данных, но не полностью управляет поведением интерфейса.

## Что входит

- Добавить управление режимом в админке.
- Подключить режим на публичной карточке товара.
- Проверить корзину и чат.
- Убедиться, что SEO-страницы и карточки не ломаются.

## Возможные режимы

### `both`

Показывать:
- кнопку добавления в корзину;
- кнопку «Написать продавцу».

Использовать как режим по умолчанию.

### `cart_only`

Показывать:
- только покупку через корзину.

Скрывать:
- основной CTA для чата.

Чат можно оставить вторичным действием, если бизнесу это нужно, но это надо согласовать.

### `cta_only`

Показывать:
- только CTA связи с продавцом.

Скрывать:
- добавление в корзину.

Подходит, если платформа пока не хочет проводить б/у заказы через checkout.

## Возможные файлы

- `frontend/my-autoparts/src/pages/PartDetail/PartDetail.jsx`
- `frontend/my-autoparts/src/pages/AdminPanel/AdminPanelPage.jsx`
- `frontend/my-autoparts/src/redux/slices/PublicInfoSlice.js`
- `backend/app/routers/admin.py`
- `backend/app/models/site_settings.py`

## Уточняющие вопросы в Plan mode

- Какой режим должен быть по умолчанию на продакшене?
- Нужно ли разрешить админу менять режим без деплоя?
- При `cta_only` нужно ли полностью скрывать корзину или только основную кнопку?
- При `cart_only` нужно ли оставить ссылку «задать вопрос продавцу»?
- Должен ли режим отличаться для новых и б/у запчастей?

## Результат этапа

- Админ может выбрать режим покупки б/у.
- Карточка товара уважает выбранный режим.
- Покупателю не показываются конфликтующие действия.

## Критерии готовности

- Настройка сохраняется и применяется после перезагрузки.
- Публичная карточка корректно выглядит во всех режимах.
- Корзина и чат не ломаются.
- Нет новых ошибок линтера.

# Этап 3. Единый и понятный путь заказа б/у запчасти

## Цель

Сделать покупку б/у запчастей понятной от карточки товара до заказа в личном кабинете.

## Почему важно

Пользователь может найти товар, но должен понимать:

- есть ли товар в наличии;
- можно ли купить сразу;
- как связаться с продавцом;
- где потом смотреть заказ;
- что происходит после оформления.

## Что входит

- Проверить текущий checkout для б/у.
- Убрать путаницу между старым `orders_legacy` и новыми sales/purchases страницами.
- Сделать понятные статусы заказа.
- Показывать пользователю следующий шаг после оформления.
- Подготовить базу для PWA/email-уведомлений.

## Не входит

- Онлайн-оплата б/у, если отдельно не согласовано.
- SMS/Telegram/WhatsApp.
- Полная переработка всех заказов новых запчастей.

## Возможные статусы

- `created` — заказ создан.
- `seller_confirming` — продавец подтверждает наличие.
- `confirmed` — заказ подтверждён.
- `ready_for_pickup` — готов к выдаче.
- `shipped` — отправлен.
- `completed` — завершён.
- `cancelled` — отменён.

Нужно проверить, какие статусы уже есть в базе и API.

## Возможные файлы

- `frontend/my-autoparts/src/pages/OrderRegistration/OrderRegistration.jsx`
- `frontend/my-autoparts/src/pages/Sales/SalesOrdersPage.jsx`
- `frontend/my-autoparts/src/pages/Sales/PurchasesOrdersPage.jsx`
- `backend/app/routers/orders_legacy.py`
- `backend/app/routers/sales.py`
- `backend/app/schemas/orders/order.py`

## Уточняющие вопросы в Plan mode

- Нужно ли сейчас проводить б/у заказ через корзину или только фиксировать заявку?
- Продавец должен подтверждать наличие перед финальным заказом?
- Какие статусы нужны в MVP?
- Нужны ли комментарии покупателя к заказу?
- Нужна ли доставка на первом этапе или только самовывоз/договорённость?
- Должен ли покупатель получать email после оформления?
- Нужно ли PWA-уведомление продавцу о новом заказе?

## Результат этапа

- Покупатель понимает, что произошло после оформления.
- Продавец видит новый заказ в рабочем разделе.
- Покупатель видит заказ в покупках.
- Нет дублирования старого и нового поведения в интерфейсе.

## Критерии готовности

- Можно оформить тестовый заказ б/у.
- Заказ виден продавцу и покупателю.
- Статусы отображаются человекочитаемо.
- Нет битых маршрутов.

# Этап 4. PWA/email-уведомления

## Цель

Добавить систему уведомлений только для PWA и email.

## Важное ограничение

На этом этапе не делать:

- SMS;
- Telegram;
- WhatsApp;
- мобильные SDK;
- сложные внешние notification-платформы.

Разрешённые каналы:

- PWA push;
- email.

## Для каких событий нужны уведомления

Минимальный набор:

- новый заказ продавцу;
- изменение статуса заказа покупателю;
- новое сообщение в чате;
- товар прошёл модерацию;
- товар отклонён модерацией;
- низкий остаток или товар закончился.

Расширенный набор:

- Avito-заказ синхронизирован;
- ошибка выгрузки Avito/Drom;
- принтер недоступен при попытке печати;
- сотруднику назначено действие;
- продавец долго не ответил покупателю.

## PWA push

Нужно проверить:

- есть ли service worker;
- как сейчас устроено PWA;
- где хранить подписки;
- как отправлять push с бэкенда;
- как пользователь будет давать разрешение.

## Email

Нужно проверить:

- какие SMTP/env уже есть;
- есть ли email verification;
- есть ли шаблоны писем;
- как логировать ошибки отправки.

## Возможные backend-компоненты

- таблица notification subscriptions;
- таблица notification events;
- сервис отправки email;
- сервис отправки web push;
- Celery-задачи для асинхронной отправки;
- настройки пользователя: какие события включены.

## Возможные frontend-компоненты

- центр уведомлений в кабинете;
- настройки уведомлений;
- баннер предложения включить PWA push;
- toast при успешной подписке;
- fallback на email, если push не разрешён.

## Возможные файлы

- `frontend/my-autoparts/public/`
- `frontend/my-autoparts/src/`
- `backend/app/routers/notifications.py`
- `backend/app/routers/websocket.py`
- `backend/app/celery_app.py`
- `backend/app/tasks/`
- `backend/app/utils/`
- `.env` файлы, но секреты не коммитить.

## Уточняющие вопросы в Plan mode

- Какие события включить в MVP уведомлений?
- Кому отправлять уведомление о новом заказе: владельцу организации, всем менеджерам или сотрудникам с правом продаж?
- Нужно ли пользователю отключать отдельные типы уведомлений?
- Email должен быть обязательным fallback, если PWA push выключен?
- Нужно ли делать HTML-шаблоны писем или достаточно простого текста?
- Какой SMTP использовать?
- Должны ли уведомления храниться в базе как история?

## Результат этапа

- Пользователь может включить PWA push.
- Система может отправить email.
- Есть минимум одно рабочее событие, например новый заказ.
- Есть безопасный fallback, если push не разрешён.

## Критерии готовности

- Подписка PWA создаётся и удаляется.
- Email уходит на тестовый адрес.
- Ошибки отправки логируются.
- Уведомления не блокируют основной запрос.
- Нет секретов в Git.

# Этап 5. Кабинет продавца: задачи вместо сухих цифр

## Цель

Сделать дашборд продавца не просто отчётом, а рабочим экраном: что требует внимания сегодня.

## Почему важно

Продавцу полезнее видеть конкретные действия:

- заказы без ответа;
- товары без фото;
- товары не выгружены на Avito;
- остаток закончился;
- товары на модерации;
- ошибки интеграций.

## Что входит

- Добавить блок «Требует внимания».
- Сгруппировать задачи по важности.
- Сделать быстрые ссылки на нужные страницы.
- Не перегружать дашборд.

## Возможные карточки

- `Новые сообщения` — перейти в чаты.
- `Ошибки Avito` — перейти в интеграцию.
- `Товары без фото` — перейти в фильтр «Мои запчасти».
- `На модерации` — перейти во вкладку модерации.
- `Закончился остаток` — перейти к товарам с нулём.
- `Не распечатаны этикетки` — если будет признак печати.

## Возможные файлы

- `backend/app/routers/sales.py`
- `backend/app/routers/products.py`
- `frontend/my-autoparts/src/redux/slices/`

## Уточняющие вопросы в Plan mode

- Какие задачи для продавца самые важные в реальной работе?
- Нужно ли показывать задачи сотрудникам с ограниченными правами?
- Нужно ли скрывать финансовые цифры от кладовщика?
- Какие задачи должны быть красными, жёлтыми, обычными?
- Нужны ли PWA/email-уведомления для критичных задач или только экран дашборда?

## Результат этапа

- На дашборде есть список действий.

- Продавец быстрее понимает, что делать.

## Критерии готовности

- Нет тяжёлых запросов при открытии дашборда.
- Данные соответствуют правам пользователя.
- Переходы работают.
- Интерфейс нормально выглядит на мобильном.

# Этап 6. Онбординг продавца

## Цель

Помочь новому продавцу пройти путь от регистрации до первой продажи.

## Почему важно

Сейчас система функциональная, но новый продавец может не понимать, что делать:

- заполнить организацию;
- дождаться модерации;
- добавить склад;
- добавить первую запчасть;
- настроить Avito;
- распечатать этикетку;
- обработать первый заказ.

## Что входит

- Экран или блок статуса после регистрации продавца.
- Чеклист настройки кабинета.
- Подсказки в дашборде.
- Чёткий статус модерации продавца.
- Скрытие недоступных действий до одобрения, если нужно.

# Этап 20. Финальный аудит перед большим релизом

## Цель

## Что проверить

- Сборка frontend.
- Backend tests, если есть.
- Линтеры.

- Миграции.
- Env-переменные.
- Права пользователей.
- SEO-страницы.
- Интеграции.

## Основные ручные сценарии

### Покупатель

- открыть главную;
- найти б/у запчасть;
- открыть карточку;
- добавить в корзину или написать продавцу;
- оформить заказ;

- написать в чат.

- открыть дашборд;

- посмотреть «Мои запчасти»;
- распечатать этикетку;
- обработать заказ;
- посмотреть финансы.

### Админ

- одобрить продавца;
- модерировать товар;
- изменить настройки сайта;
- проверить аналитику;
- проверить SEO/feeds.
