# Мобильное приложение для «Свой Гараж»: объём первого релиза и выбор стека

Документ отвечает на два вопроса: (1) что выносить в мобильное приложение в первую очередь, (2) каким стеком это строить при требуемой кроссплатформенности iOS + Android. Всё выводы опираются на текущее состояние репозитория (`celery_update`), а не на абстрактные предпочтения.

---

## 1. Что у нас уже есть и что это даёт приложению

| Факт из репозитория | Следствие для мобильного |
|---|---|
| Фронт — React 19 SPA + Redux Toolkit + React Router 7, сборка Vite 7, PWA (`public/manifest.json`, `service-worker.js`, `offline.html`) | Это уже «почти приложение»: работает офлайн-оболочка, есть иконки 192/512, уже есть отдельные мобильные вьюхи (`MobileDayPlanner`, `AutoserviceOrdersMobileView`, `html.mobile-shell` с фиксированным body и скроллом в `#root`) |
| Бизнес-логика слоя API лежит в Redux-слайсах и `utils/` на чистом JS (`apiClient.js` — обычный `fetch`) | Слайсы, схемы, хелперы дат (`autoservicePlannerLayout.js`), нормализаторы статусов переносятся в React Native без переписывания — это самый большой актив при выборе RN |
| Стили — Tailwind | В RN не переносится: нужен NativeWind или переписывание UI-слоя. Переиспользуется логика, а не разметка |
| Авторизация: access JWT 30 мин + `POST /auth/refresh` со sliding-окном refresh на 365 дней | Готовый механизм «не разлогиниваемся» для мобильного; хранить refresh надо не в localStorage, а в Keychain/Keystore (`expo-secure-store`) |
| Все сущности фильтруются по `organization_id`, права — через коды (`autoservice.planner.view/edit/caldav`, `autoservice.inspections.confirm` и т. д.) | Один и тот же бэкенд обслуживает публичного покупателя, продавца и сотрудника автосервиса — приложение ничего не «допиливает» по доступам, просто читает те же права |
| ORM/эндпоинты уже «мобильно-дружелюбные»: `GET /autoservice/dashboard/summary` (один запрос вместо пяти), `/planner/week`, `/planner/month`, `/planner/conflicts` | Не нужен отдельный «тонкий» API для мобильного — экономит недели |
| Медиа-пайплайн (фото/видео, сжатие через FFmpeg, watermark, MinIO/boto3, обработка в Celery) уже существует | Загрузка фото детали/заказа с камеры — переиспользование, а не новая разработка |
| Напоминания сейчас: CalDAV (Radicale, VEVENT/VTODO-алармы на iPhone) + SMS через `smsgold`/`smsc` с платой за сообщение | Push (FCM/APNs) — прямая замена части SMS-расходов и самый ценный «нативный» функционал приложения |
| Печать документов — только серверная (`RepairOrder*PrintPage`, `docs` о print-агентах на Windows) | В мобильном первого релиза печать не нужна: отдавать ссылку/PDF, не воспроизводить |

Вывод: backend к мобильному приложению практически готов. Вся реальная работа — это UI-слой, push-транспорт и хранение токенов.

## 2. Что выносить в первый релиз

### 2.1 Главный выбор: для кого приложение

У сервиса три аудитории: **сотрудник автосервиса** (внутренний инструмент), **продавец запчастей** (маркетплейс), **покупатель** (витрина + поиск). Все три в одно приложение нельзя — получится размытый продукт с троями сценариями навигации.

Рекомендация по порядку:

1. **Первое приложение — рабочее место сотрудника автосервиса.**
   Почему именно оно:
   - Поверхность мала и уже спроектирована: планировщик (неделя/месяц), заказ-наряды, записи на осмотр, склад, «Рабочий стол». Мобильные вьюхи для этого уже написаны — значит UX-задача частично решена.
   - Это ежедневный инструмент «в руках»: ценность от пушей и офлайна максимальна, а требования к polished-дизайну ниже, чем у публичного продукта.
   - Пользователи контролируются вами: тестирование в TestFlight/Play Internal, итерации по неделям, никакого риска отказа ревью App Store на сырой версии.
   - Оно обкатывает всю инфраструктуру, нужную позже продавцу и покупателю: безопасное хранение токенов, push-подписки, загрузка с камеры, офлайн-кэш.
2. **Второе — приложение продавца** (выкладка деталей с камеры, заявки/заказы, чат, цены). Оно уже опирается на готовый медиа-пайплайн и чат-модуль.
3. **Приложение покупателя — последним или не делать.** Витрина и поиск запчастей хорошо работают как PWA; отдельный стор-продукт имеет смысл только при критической массе повторных покупок, иначе это бесплатная поддержка третьей кодовой базы.

### 2.2 Объём MVP для сотрудника автосервиса

Берём (в порядке приоритета):

| Модуль | Что именно | Опора на существующий код |
|---|---|---|
| Вход и сессии | Логин, авто-refresh, выбор организации при нескольких | `/auth/login`, `/auth/refresh`, права из токена |
| Планировщик | Недельная сетка полосами + месячный календарь, модалка дня с группировкой по рабочим зонам, создание/правка заказ-наряда и записи прямо из ячейки, проверка конфликтов перед сохранением | `/planner/week`, `/planner/month`, `/planner/conflicts`, вся логика `autoservicePlannerLayout.js` переносится как есть |
| Push-напоминания | Запись на осмотр: за час и накануне; «подтвердите заявку»; новый заказ в моей зоне | celery-beat вместо части SMS; тот же тайминг, что уже реализован в CalDAV-алармах |
| Заказ-наряды | Список с фильтрами по статусам и зонам, карточка заказа, статусы, оплата/дебит | `GET /autoservice/repair-orders?scope=all`, сортировка по датам |
| Записи на осмотр | Список, подтверждение заявки, создание заказа из записи с автоподстановкой дат | право `autoservice.inspections.confirm`, `create_repair_order` |
| Рабочий стол | Один экран-сводка с блоками по правам | `GET /autoservice/dashboard/summary` — готовый «мобильный» контракт |
| Склад | Остатки, приход/расход, возврат из модалки позиции | `/autoservice/warehouse`, стиль-классы `autoserviceList*Class` |
| Офлайн-чтение | Кэш последнего планировщика/списка; записи только онлайн | кэш ответов + «Данные от <время>» |

Не берём в первый релиз (остаётся на вебе):

- **Отчёты и экономика** (`/autoservice/reports/*`, payroll, финансы) — wide-tables, на экране телефона читаемо не будет; это задача «посмотреть на десктопе».
- **Печать документов** (счёт, УПД, receipts) — серверная, завязана на print-агенты и термоголовки.
- **Админка и настройки** (`/admin/*`, права сотрудников, рабочие зоны, SMS-провайдеры, CalDAV-подключение) — редкие операции, высокий риск ошибочного тапа.
- **Управление правами и организациями** — то же самое.
- **Поиск запчастей Rossko/Drom/Laximo, VIN-разбор** — тяжёлые многошаговые формы со сложной фильтрацией; это продукт продавца/покупателя, не мобильного рабочего места.
- **Настройка календарной синхронизации** — CalDAV уже работает со штатным приложением «Календарь» на iPhone, дублировать это в свой UI смысла нет.

Отдельно про «хочется, но потом»: тёмная тема, виджеты домашнего экрана, Apple Watch, сканирование VIN камерой, голосовые заметки к заказу. Первые два — дешёвые, но не MVP; сканирование VIN — интересный кандидат во вторую очередь, так как VIN-парсинг (Laximo) уже в проекте.

## 3. Стек

### 3.1 Сравнение вариантов

| Вариант | Скорость до стора | Переиспользование кода | Ограничения | Цена поддержки |
|---|---|---|---|---|
| **Capacitor: нативная оболочка поверх текущей PWA** | Очень быстро (1–3 недели): тот же билд Vite, плюс `@capacitor/push-notifications`, `camera`, `secure-storage`, `network-status` | ~100% существующего фронта | Это WebView: жёстче анимации, нет нативных жестов/списков, App Store может завернуть как «thin wrapper» — реальный риск для публичного релиза; iOS-шрифт-метрик и клавиатура требуют доводки | Дёшево, но потолок качества — «веб в рамке» |
| **React Native + Expo (рекомендуется)** | Средне (6–10 недель до первого внутреннего релиза) | Высокое: Redux Toolkit-слайсы, `fetch`-клиент, весь чистый JS в `utils/` переносятся 1:1; не переносится только Tailwind-разметка | Нужен нативный UI-слой (NativeWind/Restyle), отдельный CI через EAS Build; периодические мажорные апгрейды RN | Одна кодовая база iOS+Android, предсказуемо |
| **Flutter** | Средне-долго | Нулевое: весь фронт переписывается на Dart, JS-логика и слайсы теряются | Своя экосистема, чужая проекту; команды, знающие React, переучиваются | Две парадигмы в компании навсегда |
| **Нативно (Swift + Kotlin)** | Долго | Нулевое | Два приложения вместо одного — прямо против требования кроссплатформенности | Максимальная |
| **PWA / TWA (Android-only)** | Дёшево | 100% | iOS: push доступны только с 16.4 и только после установки на домашний экран, платёж и «ощущение приложения» слабее | Не закрывает задачу iOS как полноценный продукт |

### 3.2 Рекомендация

**React Native + Expo** (свежий стабильный Expo SDK, версия React Native берётся из него; конкретные версии пиновать по правилу AGENTS.md — зависимости старше 7 дней, без плавающих диапазонов).

Причины именно для этого проекта:

1. **Переиспользование логики, а не только кода.** Планировщик — самая сложная часть продукта — это чистые функции над датами (`getWeekStart`, `assignPlannerLanes`, `plannerItemEndDate` с `OPEN_ORDER_STATUSES`, `plannerItemCoversDay`, `plannerMonthZoneSections`) плюс Redux-слайсы. В RN они переезжают без изменений; в Flutter их пришлось бы переводить и повторно отлаживать. Тесты (`autoservicePlannerLayout.test.js`, Vitest) продолжают защищать обе платформы.
2. **Один язык и один пул знаний.** Стек проекта — React/Redux; Flutter потребовал бы отдельную компетенцию и удвоил бы стоимость каждой бизнес-фичи («сделали на вебе → ещё раз на Dart»).
3. **Expo закрывает именно то, ради чего нужно нативное приложение**: EAS Build и EAS Submit (сборка и подача в оба стора без локальных Xcode/Android-студий), `expo-notifications` поверх FCM/APNs, `expo-secure-store` для refresh-токена, `expo-image-picker`/camera для загрузки в существующий MinIO-пайплайн, OTA-обновления (expo-updates) — можно править JS-слой без пересборки и ревью стора, что для внутреннего инструмента сотрудника критично по скорости итераций.
4. **Дольше живут детали.** Нативные списки (`FlashList`/`FlatList`) для планировщика и заказ-нарядов, pull-to-refresh, свайп дня в мобильном планировщике — то, что в WebView либо работает плохо, либо не работает.
5. **Exit-путь в веб.** `react-native-web` даёт возможность со временем отдавать часть экранов в браузер без дублирования, а не наоборот.

Что стоит взять из библиотек (списать точные версии при старте): `expo` + `expo-router` (навигация), `@reduxjs/toolkit` + `react-redux` (уже наши), `NativeWind` (перенос дизайн-токенов `brand/ink/line/surface`, `rounded-sg*`, `shadow-sg*`), `expo-secure-store`, `expo-notifications`, `expo-image-picker`, `@react-native-async-storage/async-storage` (кэш планировщика), `react-native-config` (`EXPO_PUBLIC_API_BASE_URL`).

### 3.3 Промежуточный вариант, если нужен «галочка в сторе» за месяц

Собрать **Capacitor-оболочку поверх текущего билда** только под внутреннее использование (TestFlight/Play Internal): пуши на события `dashboard/summary` и вход через SecureStore. Это даёт обратную связь от сотрудников сразу, но рассматривать её надо как одноразовый разведочный шип, а не как базу: параллельно вести RN-версию, и как только RN-планировщик покроет ежедневные сценарии — Capacitor-сборку снять. Держать оба долго — платить дважды за каждый UI-фикс.

## 4. Что доработать на бэкенде под приложение

Немного, но по делу:

1. **Push-подписки.** Новая таблица `device_tokens` (user_id, platform `ios|android`, token, app_version, active) + `POST/DELETE /mobile/device-tokens`; Celery-задача обхода будущих записей и отправки через FCM/APNs. Идеологически это следующий шаг, уже помеченный в AGENTS.md как «авто-напоминания — следующий этап»: пуш вытесняет часть платных SMS, поэтому экономика на стороне сокращения расходов `smsgold`/`smsc`.
2. **Хранение токенов.** Refresh-токен — в Keychain/Keystore; на вебе остаётся localStorage. Одинаковый контракт `/auth/refresh`, никаких новых эндпоинтов.
3. **Версионирование клиентов.** Заголовок `X-App-Version` (или `User-Agent`) и минимальная поддерживаемая версия в `site_settings`, чтобы можно было заставить обновиться при несовместимом контракте.
4. **Идемпотентность записи из планировщика.** Мобильные сохранения идут по плохому интернету; создать заказ-наряд/запись повторно из-за ретрая — реальный сценарий. Достаточно клиентского `Idempotency-Key` на `POST /autoservice/repair-orders` и `POST .../inspection-bookings` с короткой дедупликацией на стороне бэкенда.
5. **CORS / `Access-Control-Allow-Origin`** — нужны только если остаётся Capacitor/WebView-вариант; чистый RN ходит `fetch` без префлайтов.
6. **Отдача часового пояса.** На проде уже Asia/Yekaterinburg; приложение должно брать таймзону из ответа/конфига, а не из устройства, иначе полосы планировщика разъедутся.

## 5. План по этапам

| Этап | Содержание | Ориентир |
|---|---|---|
| 0. Спайк | Expo-скелет: вход, refresh из SecureStore, один запрос к `/autoservice/planner/week`, экран-сетка из 3 строк. Цель — подтвердить перенос слайсов и NativeWind-токенов | 1 неделя |
| 1. Каркас | Навигация по правам (тот же чек `autoservice.*`), «Рабочий стол» из `dashboard/summary`, список заказ-нарядов, тёмная/светлая база, CI на EAS | 2 недели |
| 2. Планировщик | Недельные полосы и месячная сетка на перенесённых функциях `autoservicePlannerLayout.js`, модалка дня по зонам, создание/правка заказа и записи, конфликты | 2–3 недели |
| 3. Push + записи | Подписки устройства, напоминания за час/накануне, подтверждение заявки из пуша, вытеснение части SMS | 1–2 недели |
| 4. Склад + офлайн | Остатки, приход/расход, возврат; кэш планировщика и списков с меткой времени | 2 недели |
| 5. Внутренний релиз | TestFlight + Play Internal, сбор фидбека от сотрудников, OTA-правки | 1 неделя + постоянно |
| 6. Приложение продавца | Выкладка с камеры (существующий медиа-пайплайн), заявки, чат, цены | следующий цикл |

Итого до осмысленного внутреннего релиза — около 8–10 недель одним разработчиком (или 5–6 вдвоём), при том что backend-работа укладывается в ~1 неделю.

## 6. Риски и как их снимать

- **App Store для «внутреннего инструмента».** Формально разрешено, но ревью может спросить демонстрационный аккаунт и ценность относительно веба. Снимается: TestFlight на первом этапе, потом релиз с описанием роли и тестовыми доступами.
- **Две UI-базы (веб + RN) и расходящийся UX.** Снимается тем, что логика (слайсы, utils, тесты) общая, а дизайн-токены вынесены в один источник, который NativeWind читает; плюс правило: контракт эндпоинта меняется вместе с обоими клиентами в одном PR.
- **Tailwind-перенос.** Не переносится разметка — ревью объёма UI-работ надо делать после этапа 0, а не по наитию.
- **Оптимистичные правки планировщика офлайн.** Полосы меняют даты, а конфликты считаются на сервере; в MVP офлайн — только чтение, изменения строго онлайн. Это ограничение надо зафиксировать в скоупе, а не «доделывать потом».
- **Плохая сеть на объекте.** Все списки — со `limit/offset` и кэшем; планировщик уже отдаётся одним запросом за неделю/месяц, что удачно.
- **Раздувание MVP.** Единственный надёжный фильтр: экран попадает в релиз, только если сотрудник пользуется им каждый день на планшете/телефоне, а не «раз в квартал на десктопе».

## 7. Итог одной строкой

Первое приложение — рабочее место сотрудника автосервиса (планировщик, заказ-наряды, записи, рабочий стол, склад, push-напоминания вместо части SMS; отчёты, админка, печать и поиск запчастей остаются на вебе), строить на **React Native + Expo** с переносом существующих Redux-слайсов и JS-утилит планировщика, потому что Flutter означал бы потерю всей уже написанной логики, а Capacitor-оболочка — потолок качества и риск отказа ревью.
