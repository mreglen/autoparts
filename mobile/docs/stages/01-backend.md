## 2. Работа 1.1 — пагинация там, где её нет

### 2.1 Форма ответа — принято 06.11.2026: отдельный `…/page`-маршрут

Требование «без параметров ответ обязан остаться прежним» конфликтует с тем, что списки сейчас отдают голый
`list[…]`, а не объект. Выбран вариант **B**: старый маршрут не трогается вообще, новый `GET …/page` отдаёт
только обёртку `{items,total,has_more,fetched_at}`.

Как этого добиться без дублирования логики: фильтры выносятся в общий dependency-класс (например
`OrderListFilters`), функция выборки остаётся одна, у двух роутеров различается только хвост — старый возвращает
`list[View]`, новый `PageView`. Для генератора клиента у каждого метода ровно один тип ответа, `anyOf` в
TypeScript не появляется. Отказ от «объект везде + правка веба» — нарушение правила 1 на пилоте.

### 2.3 Обязательные поля нового ответа

```
{ items: […], total: int, has_more: bool, fetched_at: "2026-11-06T14:20:31" }
```

`fetched_at` — время сервера на момент сборки ответа. Без него приложение не может честно показать «данные от
14:20» (правило 7 раздела 1 карты), а времени телефона доверять нельзя (см. 3.1). `total` при Python-фильтре
(статус оплаты) считается по отобранному списку, как уже сделано в `list_repair_orders`, а не по SQL.

## 3. Работа 1.2, 1.3 и 1.8 — один эндпоинт `/api/mobile/meta` вместо трёх догадок

Все три пункта карты (правило по таймзонам, абсолютные URL, версия/адрес APK) сводятся к одному маленькому
эндпоинту, и это единственный способ решить их, не трогая существующие ответы:

```
{
  "server_time": "2026-11-06T14:20:31",
  "timezone": "Europe/Moscow",
  "utc_offset_minutes": 180,
  "public_base_url": "https://svoygarage.ru",
  "min_supported_app_version": "1.0.0",
  "latest_apk": { "version": "1.4.2", "url": "…", "notes": "…" }
}
```

Доступ — аутентифицированный. Значения берутся из `PUBLIC_BASE_URL` (`core/config.py:27`) и из `site_settings`
(раздел 14, открытое 3). Описывается Pydantic-схемой, `API_DOCS_ENABLED` для него не нужен.

### 3.1 1.2 — правило по таймзонам фиксируем как есть

Одно предложение, которое потом цитирует клиент: **все `datetime` в ответах — наивный wall-clock
Europe/Moscow, смещения в строке нет и не будет.** Это следует из `normalize_dt` (раздел 1 таблицы), который
обрезает `tzinfo` вместо пересчёта, и из того, что `scheduled_end_at`/`status_*_at` на проде — TIMESTAMPTZ, а
пишутся `datetime.now()` по МСК (AGENTS.md 7.6). Разойтись с наследием «по-взрослому» (явный offset в JSON)
можно только переписав сериализацию глобально, а это ломает веб, где даты местами сравнивают как строки.
Пилот этого не прощает (решение 0.9) — поэтому правилу соответствует клиент:

- один хелпер `parseMskWallClock(iso)`, навешивающий смещение из `meta`;
- прямой `new Date(isoString)` для полей БД запрещён: JS трактует строку без смещения как **локальное** время
  устройства, и телефон с UTC в настройках покажет заказ на 3 часа раньше;
- тест на разбор даты с `TZ=UTC` обязан падать, если хелпер убрать.

### 3.2 1.3 — абсолютные URL файлов не внедряем в ответы

`main.py:978-1049` монтирует `/uploads`, `/pictures`, `/videos`, `/vehicle_pictures` и `/media/{path}`, пути в
БД относительные. Подстановка абсолютных URL в ответы задела бы весь веб-код, который эти пути режет и
склеивает сам (`apiClient.js:36-63`). Клиент доклеивает `public_base_url` из `meta`. Пункт карты 1.3 таким
образом закрывается без правки существующих схем; в карте (`PLAN.md`, пункт 1.3) это уже отражено.

### 3.3 1.8 — обновления приложения

`min_supported_app_version` + `latest_apk` в `meta` питают этап 17 карты (доставка APK по ссылке и экран «есть
обновление»). Больше эндпоинта версий нигде не заводим.

## 4. Работа 1.4 — опрос статуса фоновых задач для автосервиса

Есть только для upload (`routers/upload.py:775, 985`). Приложению нужно то же для:

| Операция | Сейчас | Что сделать |
|---|---|---|
| Импорт из покупок на склад | `POST /autoservice/warehouse/from-purchases` синхронный (`autoservice_warehouse.py:1187-1217`), `task_id` не отдаётся | оставить синхронным (раздел 14, открытое 1) или `?background=true` → `{task_id}` + статус |
| Обратный синк календаря | `POST /autoservice/calendar-sync/sync-from-calendar` возвращает `task_id` (`autoservice_caldav.py:108-115`), но статуса нет | общий эндпоинт статуса |
| Обработка фото/видео | `photo-status` / `video-status` | переиспользуем как есть |
| CalDAV-синк по beat, Drom-сверка | внутренние задачи (`tasks/autoservice_caldav_tasks.py`, `tasks/drom_tasks.py`) | клиенту не отдаём |

Форма: `GET /api/tasks/{task_id}` → `{ "state": "PENDING|STARTED|SUCCESS|FAILURE|REVOKED", "progress": …?, "result": …?, "error": …? }`.

Три обязательных условия, иначе получится дыра:

1. **Скоуп по организации.** `AsyncResult` про права ничего не знает. При постановке задачи писать владельца в
   Redis (`task_owner:{task_id}` с TTL = `result_expires`) и сверять с запрашивающим. Без этого любой
   аутентифицированный пользователь перебором `task_id` читает чужие результаты.
2. **`error` — человекочитаемо и без стека.** На `FAILURE` обязан быть `detail`, который можно показать в `Toast`.
3. **Протухание.** `PENDING` дольше N минут или отсутствие ключа → клиент пишет «задача утрачена, проверьте
   результат в списке», а не крутит спиннер вечно (`result_expires=3600`, `celery_app.py:58`).

## 5. Работа 1.5 — серверный PDF печатных форм

Механизм уже работает на проде в соседнем месте (`printers.py:284` `_render_label_pdf_bytes` +
`utils/render_label_pdf.py`), поэтому задача звучит как «обобщить и добавить макеты», а не «прикрутить
библиотеку». `playwright==1.58.0` и Jinja2 уже в зависимостях, Chromium на сервере используется тем же путём —
новых системных пакетов не предвидится, но шрифт и кириллицу проверяем на сервере (критерий 12.6).

(`GET /autoservice/repair-orders/{id}`, `autoservice_repair_orders.py:1759`) плюс `state.organization.data`

| Счёт | `RepairOrderInvoicePrintPage.jsx` | 653 |
| УПД | `RepairOrderUpdPrintPage.jsx` | 957 |

2805 строк разметки — это и есть настоящая цена пункта: макеты верстаются заново как Jinja-HTML с print-CSS,

### 5.2 Эндпоинты

```

    → application/pdf, Content-Disposition: attachment; filename="№16-заказ-наряд.pdf"
```

Права — как у карточки заказа; скачивание пишет событие аудита по образцу `_log_report_export`
(`autoservice_finance.py:63-78`). **Принято 06.11.2026: генерация синхронная, в ответе запроса** — готовый путь
`printers.py` уже решает проблему конкурентности (см. 5.3), Celery-обёртка добавила бы полдня работы и
задержку на каждом маленьком документе. Если замер на проде покажет, что УПД на сотню позиций не влезает в
разумное время, для него одного возвращаемся к фоновой задаче — это ветка, а не план.

### 5.3 Что именно переиспользуем и чего ждать

Существующий путь рендера уже решает главную проблему — он не держит Chromium в процессе API:
`_html_to_pdf_bytes` (`routers/printers.py:252-274`) запускает `render_label_pdf.py` отдельным процессом,
`_render_label_pdf_bytes` (`:284-286`) оборачивает это в `asyncio.to_thread`, а
`MAX_CONCURRENT_LABEL_PDF_RENDERS = max(2, min(8, cpu_count))` (`:48`) не даёт рендерам задушить сервис.
Плюс воркеры на проде асинхронные (`docs/ops/kroan.service`: UvicornWorker, `-w 3`, `--timeout 120`), поэтому блокировки event loop нет. Заказные формы идут тем же путём —
свой semaphore-счётчик и `to_thread`, ничего нового в инфраструктуру не добавляем.

Что механизм не отменяет:

- **Кириллица и `₽`/`№`.** Рендер живёт в отдельном процессе на том же Ubuntu: нужен шрифт с кириллицей,
  установленный в образе. Дефолт Headless Chromium на минимальной системе отдаёт квадратики. Мерить на
  сервере, а не локально на Windows, где шрифтов хватает.
- **Память.** Каждый рендер — процесс Chromium примерно на 150–250 МБ; при `-w 3` и semaphore до 8 это пик,
  который надо сравнить со свободной RAM на проде до включения фичи.
- **Арифметика обязана быть общей.** `grand_total`, `discount_percent`, НДС — через `_order_grand_total` /
  `_discount_factor`, а не пересчётом в шаблоне, иначе PDF разойдётся с экраном. Это правило 6 раздела 1
  карты: паритет поведению, не пикселям.
- **`--timeout 120` — не лицензия на медленный рендер:** цель — документ до 3 секунд, иначе очередь из
  скачиваний на 8 слотов видна пользователю как «нажал и ждёт».

Веб-печать в этом этапе не трогаем: `window.print()` остаётся эталоном, пока PDF не сверен лист в лист.

### 5.4 Реализовано 06.11.2026 — заказ-наряд

- Маршрут `GET /api/autoservice/repair-orders/{id}/pdf` (`autoservice_repair_orders.py:1780`): права ровно как у
  карточки (`require_orders_access` + `_get_visible_order_or_404`), ответ `application/pdf`, обязательные
  реквизиты — `400 «Заполните: Номер заказ-наряда, …»` тем же списком, что фронт блокирует на кнопке «Печать»,

## 7. Работа 1.7 — ревизия rate-limit и сессионных лимитов под мобильные сети

Фактура: `RateLimitMiddleware` (`main.py:457-502`) берёт правила из
`middleware/rate_limit_middleware.py:21-40`, ключ — `f"{prefix}:{ip}"` (`utils/rate_limit.py:68-75`), IP —
первый элемент `X-Forwarded-For` (`:26-32`), счётчик fixed-window в Redis, при недоступности Redis лимит
отпускает (`:56-58`). `RATE_LIMIT_ENABLED` по умолчанию `True` (`core/config.py:134`).

Две вещи, которые на пилоте обязательно сработают:

1. **`/api/auth/login` — 10 запросов на 900 секунд с IP.** Все сотрудники автосервиса сидят за одним
   операторским NAT. Шесть телефонов, у которых за 15 минут слетели refresh-токены (правка прав гасит все
   сессии сотрудника — `routers/employees.py:244-247`; перенос дампа прод-БД — тем более),
   дают 429 «Слишком много попыток входа» на седьмом и дальше для всех. Веб это терпит, потому что логинятся
   редко; приложение с автологином — нет.
2. **`/api/` — 600 запросов в минуту на IP.** Холодный старт приложения, который решает «прогреть офлайн»
   (этап 3 карты), — это десятки запросов на устройство. Пять телефонов в офисе плюс открытый веб-клиент
   легко берут 600/мин, и лимит сечёт их всех разом, включая веб.

Что делаем (принято 06.11.2026):

- **Ключ с идентичностью.** Для запросов с Bearer-токеном ключ = `{prefix}:{sha1(token)}` вместо IP:
  честный лимит на пользователя, а не на чужой NAT. Анонимные пути (`/api/public/*`) остаются по IP — там
  защита от скрапперов нужнее.
- **Отдельное правило на `/api/auth/login`** с ключом по хешу логина + IP, порог поднят до 40/15 мин.
  Анти-брутфорс держим на стороне аккаунта, а не IP: аргон2-проверка уже есть, а 10-на-15-минут по IP ломает
  легитимных пользователей сильнее атакующего. Реализовано в самом роуте (`enforce_login_rate_limit`,
  `routers/auth.py`) — middleware тела запроса не читает; IP-правило в `DEFAULT_RATE_LIMIT_RULES` поднято до
  200/900 и осталось только как защита от флуда.
- **Правило для клиента фиксируем здесь же:** никакого «прогрев всего на старте». Списки подтягиваются при
  первом открытии экрана, `limit` по умолчанию 50. Это дешевле, чем поднимать лимиты, и не зависит от того,
  сколько телефонов в офисе.
- **`Retry-After` обязан доходить и читаться.** Заголовок уже формируется (`utils/rate_limit.py:78-79`),
  клиент на 429 ставит backoff и показывает «много запросов», а не «нет сети».
- **Сессии.** На каждом логине (`routers/auth.py:334-335, 504-506`) вызывается
  `cleanup_old_user_sessions(db, user.id, ip_address)` (`core/auth.py:233-246`): среди сессий этого
  пользователя **с этого IP** остаются пять по `created_at desc`, остальные удаляются строкой `db.delete` —
  не деактивируются, а удаляются, так что refresh-токен устройства умирает навсегда, и молча
  переаутентифицироваться приложение не сможет. Мобильный клиент + веб + планшет + переустановка приложения —
  это те же пять мест, а самое старое из них почти всегда телефон: он был установлен раньше, чем открыта
  очередная вкладка.
  **Принято: лимит не трогаем, меняем порядок вытеснения.** Различать платформу по `device_info` нельзя —
  это строка из формы логина, её пишет сам клиент. Поэтому на логине из заголовка `X-App-Platform` в
  `user_sessions.client_kind` пишется `ios`/`android` (у веба — NULL), и сортировка в
  `cleanup_old_user_sessions` (`core/auth.py:233`) становится «сначала веб, мобильные в конце». Проверяется
  тестом: пять открытых вкладок сайта больше не могут выбить сотрудника из приложения
  (`tests/test_mobile_backend_foundation.py`).

## 8. Работа 1.9 (в карте её нет, но без неё кодоген не взлетит) — контрактная гигиена

- `API_DOCS_ENABLED=False` в проде (`core/config.py:136`) — правильно. OpenAPI генерим в CI импортом
  приложения, не с прода.
- Перед генерацией клиента пройтись по эндпоинтам раздела 2 и убедиться, что у каждого стоит `response_model`
  или аннотация возврата: в `autoservice_finance.py` на 10 GET-маршрутов 6 `response_model`, в
  `autoservice_applications.py` на 2 маршрута — 0. Маршрут без схемы = `any` в клиенте = потерянный смысл
  генерации.
- Повторяющиеся `list[str]` (`status`, `work_zone_id`, `payment`) генератор обязан выложить как
  `?status=a&status=b`; проверяем на сгенерированном клиенте до того, как под него написаны хуки.
- Теги и `operationId` покрывают только мобильные маршруты: клиент генерится фильтром по тегу, иначе в
  TypeScript переедет весь API сайта, включая админку.

### 8.1 Реализовано 06.11.2026

- Схемы проставлены по факту, а не по памяти: инвентарь `app.routes` показал, что в `autoservice_finance.py`
  все JSON-GET уже были с `response_model`, а без схемы оставались пять `.xlsx`-экспортов и три маршрута
  заявок. Итог:
  - `autoservice_applications.py` — `/tariff-info` → `AutoserviceTariffInfoView`, `/me` →
    `AutoserviceApplicationMeView`, `POST ""` → `AutoserviceTariffApplicationOut`;
  - `GET /autoservice/clients/me/orgs` → `list[AutoserviceClientOrgBrief]` (ключи взяты из
    `list_my_autoservice_client_orgs`, проверено на живой строке локальной БД — потерь нет);
  - `POST /autoservice/calendar-sync/sync-from-calendar` → `CaldavSyncTaskView`;
  - `PUT /organizations/{org_id}/employee-cards/{card_id}/permissions` →
    `OrganizationEmployeeCardPermissionsResponse`;
  - `.xlsx`-экспорты получили `response_class=Response` + `responses=XLSX_RESPONSES`, поэтому в контракте у
    них ровно один media type (`…spreadsheetml.sheet`), а не `application/json` рядом с файлом. Та же форма
    записи уже использовалась для PDF заказ-наряда.
- Повторяющиеся `list[str]` помечены `explode=True` (`autoservice_repair_orders.py:1627-1630`): FastAPI пишет
  `explode` внутрь схемы, а не в объект параметра, но и так, и так итоговая сериализация —
  `?status=a&status=b`, потому что дефолт OpenAPI для query-массива это `form` + `explode: true`. Других
  `list[*]`-параметров в мобильной зоне нет (проверено грепом по `app/routers`).
- сторожок: `backend/tests/test_openapi_contract_hygiene.py` (26 маршрутов → обязательная схема ответа,
  бинарные → ровно свой media type, массивы → form/explode, page-маршруты → конверт
  `items/total/has_more/fetched_at`). Тест работает по `app.openapi()`, то есть по тому же контракту, из
  которого генерится клиент.
- Не сделано сознательно: теги/`operationId` под фильтр кодогена. Пока мобильного клиента нет, неизвестен
  конкретный генератор и его правила именования — правка 30+ маршрутов «под будущий фильтр» сейчас это churn.
  Делается вместе с этапом, где появляется сгенерированный клиент.
- Не тронуты схемы ответов в `auth.py` (`{"msg": …}`, `/auth/public-site-config`): их читает веб и публичная
  витрина, а мобильная роль авторизуется через `login/refresh/me`, где схемы уже есть. Типизация этих маршрутов
  — этап авторизации мобильного клиента.
- Локальная БД отстает по схеме: у `autoservice_tariff_applications` нет `contact_phone`, поэтому `/me` локально
  отвечает 500 ещё до моих правок. Проверка ключей для этого маршрута сделана по литералам возврата, а не
  прогоном на локальных данных.

## 9. Состояния, которые обязан возвращать бэкенд и различать клиент

| Ситуация | Код / тело | Действие клиента |
|---|---|---|
| Токен истёк | 401 | молчаливый `POST /auth/refresh` + повтор (механизм есть на вебе, `apiClient.js:136-141`) |
| Сессия инвалидирована (смена прав, вытеснение с 6-го устройства) | 401 + отдельный признак | выход в логин с объяснением, не «проверьте сеть» |
| Нет права на раздел/зону | 403 | экран «нет доступа»; кнопок не рисуем вовсе (права из токена) |
| Заказ закрыт, править нельзя | 400 (уже так) | гасить действия до отправки (этап 9 карты) |
| Конфликт планировщика | `GET /autoservice/planner/conflicts` перед PATCH | ConfirmDialog |
| Неверный формат поля | 422 `detail[]` | ошибки полей формы по `loc` |
| Превышен лимит | 429 + `Retry-After` | backoff, отдельный текст (раздел 7) |
| Список пуст | 200, `items: []`, `total: 0` | «нет записей», не «ошибка загрузки» |
| Ответа нет | сети нет | кэш + метка возраста из `fetched_at` |

Формат ошибки — стандартный FastAPI `{"detail": …}`; в этапе 1 не меняем, но ни один новый эндпоинт из него
не должен вылезать, иначе клиентская разборка ветвится.

## 12. Критерии приёмки

1. Сгенерированный из OpenAPI TypeScript-клиент компилируется, и ни один метод этапа 1 не отдаёт `any`.
2. Старый маршрут каждого эндпоинта из раздела 2 отвечает байт в байт как до правки (сравнение на реальных
   данных своей организации), новый `…/page` на тех же фильтрах отдаёт `total`, равный числу строк в вебе, и
   `has_more`, совпадающее с «есть следующая страница».
3. Прогнан веб-сценарий каждого затронутого раздела (заказ-наряды, склад, записи, клиенты, сотрудники,
   финансы, отчёты): строки и поведение не изменились.
4. `reports/*` на максимальном реальном периоде (12 месяцев) отвечает быстрее 2 секунд и влезает в ответ —
   иначе пагинацию отчётов переносим в этот же этап.
5. `/api/mobile/meta` отдаёт таймзону, смещение и `public_base_url`; тест разбора даты падает без хелпера при
   `TZ=UTC` на устройстве.
6. PDF заказ-наряда: кириллица и `₽` рендерятся (проверено на сервере, не локально), `grand_total` и скидки
   равны числам на экране, заказ на 30+ позиций переносится без потери итогов; два параллельных запроса не
   дают 504 (`journalctl -u kroan`).
7. `GET /tasks/{task_id}` чужой задачи отвечает 403/404, и есть тест, который это сторожит.
8. Шесть устройств с одного IP делают по одному логину в 15 минут — 429 нет. Тест или прогон на проде с
   реальным NAT.
9. В логах прод-запросов виден `X-App-Version`; `min_supported_app_version` меняётся без релиза сервера.
10. Ни одна правка не задела веб: `git diff` по `frontend/` пуст, кроме, возможно, заголовка версии в
    `apiClient.js`.
11. Тест вытеснения сессий: у пользователя с одного IP пять активных веб-сессий и одна мобильная, шестой
    веб-логин оставляет мобильную сессию живой (её refresh-токен по-прежнему работает).

Что уже закрыто локально (06.11.2026): 2 — `test_autoservice_list_pagination` (10 тестов сверяют `total` с
числом строк без окна и `has_more` на последней странице), 5 и 7 и 11 — `test_mobile_backend_foundation`
(23 теста), 6 частично — заказ-наряд реально собирается в PDF на четырёх боевых заказах локальной БД и по
тестам совпадает с веб-форматом цифр, 10 — `git status frontend/` пуст. Остальное (1, 3, 4, 8, 9 и «кириллица
на сервере» из 6) требует прод-замера или сгенерированного клиента и в локальный прогон не укладывается.

## 13. Риски

- **PDF — единственный пункт этапа, способный задеть прод под нагрузкой**, но риск ниже, чем казалось:
  рендер и так идёт отдельным процессом под semaphore (`printers.py:252-286`), решение «синхронно» принято.
  Опасно другое: шрифт без кириллицы и пик памяти на восьми параллельных рендерах.
- **Дыра при опросе задач** — забыть скоуп-ключ значит отдать чужие результаты; это сторожит тест, а не
  аккуратность.
- **Лимиты 600/мин и 10-логинов/15-мин** — если их не трогать, пилот начнётся с «приложение само выкидывает»,
  и виноватым окажется мобильный клиент.
- **Раздувание ответов отчётов** — соблазн порезать годовой `order-economics` = сломать веб.
- **Разные имена фильтров** (`supplier` vs `q` vs `include_inactive`) перейдут в клиент как есть и останутся
  навсегда: переименовывать сейчас (ломает веб) или никогда. Выбираем «никогда», иначе правило 1 нарушено.
- **2805 строк печатной разметки** — реальный объём 1.5; если судить о нём по «механизм же есть», этап сдвинет
  середину карты.

1. **Импорт из покупок** (`from-purchases`, сейчас синхронный): оставляем синхронным, и тогда 1.4 нужен только
