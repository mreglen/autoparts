# Этап 29 — Чат клиент ↔ автосервис

План этапа из `mobile/docs/PLAN-client.md`. Статус: **планирование** (16.11.2026).
Этап опциональный для v1; решение о scope — за пользователем.

## Что выяснено при исследовании

- **Готового чата «клиент ↔ автосервис» на бэкенде нет.** Существующий
  `app/routers/chats.py` (`/api/chats`) — чаты покупатель↔продавец (товары,
  `product_id`, buyer/seller) и групповые чаты организаций для сотрудников
  (`organization_chat_service`, участники = user'ы организации). Клиент
  автосервиса (`AutoserviceClient`, часто без привязки к user-сотрудникам)
  в этот механизм не входит: он не знает `user_id` сотрудников, а org-chat
  доступен только участникам-учёткам организации.
- **Модели чата уже есть и переиспользуемы:** `Chat` (есть `organization_id`,
  `chat_type`, `participants`), `Message`, `ChatMedia`, `ChatParticipant`,
  `ChatBlockedUser`. WebSocket-мост `websocket.py` существует для web-клиентов.
- **Уведомления:** `EVENT_CHAT_MESSAGE` уже маршрутизируется через
  `dispatch_user_notification` → с этапа 28 автоматически пишется в in-app ленту.
- **Медиа:** `POST /chats/{id}/messages/upload-media` + `GET /chats/media/{id}`
  (+thumbnail) уже реализованы и работают с файлами — для клиента нужно
  проверить доступ (chat_access) и при необходимости свой upload-эндпоинт.

## Варианты scope (нужно решение)

### Вариант A — «Минимальный v1» (рекомендуется)

Тред «клиент ↔ автосервис» **на организацию** (один диалог на СТО, из которого
клиент записывался/имеет гараж):

- Backend (аддитивно, новый router `autoservice_client_chats.py` или расширение
  `chats.py`):
  - `GET /autoservice/client-chats` — список диалогов клиента по его
    `AutoserviceClient`-карточкам (org, последнее сообщение, unread);
  - `GET|POST /autoservice/client-chats/{org_id}/messages` — история/отправка
    текста; сообщение адресовано «команде СТО» — читают сотрудники с
    подходящим permission (inspections/clients), отвечают через существующий
    web-чат или новый staff-экран позже;
  - участники: клиент (user_id) + «виртуальная» сторона СТО — через
    `Chat.organization_id` + `chat_type="client_service"`, сотрудники видят
    через permission, без добавления каждого в participants;
  - доступ к медиа — отдельным этапом/фоллоу-апом.
- Mobile: список диалогов (из «Ещё»/из карточки записи), экран переписки
  (текст, статусы отправки, **polling** раз в ~10–15 сек — WebSocket в Expo Go
  есть, но polling проще и надёжнее для v1), вход «Написать в сервис» из
  `ClientBookingsScreen`/карточки СТО в `ClientMoreScreen`.
- Офлайн: чтение последних сообщений из кэша; отправка только онлайн
  (очередь — отдельный этап, как у остальных write-операций).

Оценка: backend ~2–3 дня, mobile ~2–3 дня.

### Вариант B — «Полный»

Всё из A + фото/файлы (переиспользовать media-инфраструктуру), офлайн-очередь
исходящих, WebSocket-реалтайм (socket.io/WS мост), непрочитанные по диалогам,
статусы «печатает…», вход из карточки конкретной записи/заказ-наряда
(тред на booking/order вместо org). Оценка: 1.5–2 недели.

### Вариант C — «Пропустить»

Чат не делаем в v1; этап помечается отложенным. Ядро (гараж/история/запись/
уведомления/профиль) этого не требует.

## Рекомендация

Вариант A: даёт клиенту реальную ценность (вопрос по записи/заказу) без
недели работы над медиа и офлайн-очередью. Медиа и реалтайм — отдельным
этапом 29.1 при необходимости.

## Открытые вопросы для backend-части

1. Тред на организацию или на конкретную запись/заказ-наряд? (A: на организацию —
   проще; B: на сущность — контекстнее.)
2. Кто на стороне СТО читает: все с `inspections`-permission или отдельное
   право? Предлагаю — `AUTOSERVICE_PERMISSION_INSPECTIONS` (записи и есть
   основной повод писать).
3. Нужен ли web-UI для сотрудников в этом этапе или только API
   (сотрудники отвечают через существующий `/api/chats` web-интерфейс —
   потребует маппинга chat_type)? Минимум жизнеспособного: API + mobile,
   staff-экран позже.
