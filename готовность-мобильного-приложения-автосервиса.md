# Готовность проекта «Свой Гараж» к мобильному приложению автосервиса

Отчёт по аудиту кода. Дата: 06.11.2026. Ветка на момент аудита: `celery_update`.
Цель: отдельное приложение для iOS и Android с полной ролью «автосервис» + существующей ролью «клиент». Админка, интеграции и moderation остаются на сайте.

---

## 1. Итог одной фразой

Бэкенд готов примерно на 70%: авторизация, права и контракты API уже «мобильные» и переиспользуются как есть. Не готовы четыре вещи — вход клиента без email, пагинация, нативный push и печатные формы; плюс одна дыба безопасности в клиентском скоупе. Структура фронтенда к переносу не готова совсем: мобильной версии как продукта нет, есть адаптив десктопных страниц (4 отдельных `*MobileView` на 710 файлов).

## 2. Что уже готово и трогать не нужно

### 2.1 Авторизация — транспорт правильный

| Факт | Где |
|---|---|
| Bearer JWT, не куки | `backend/app/core/auth.py:18` (`OAuth2PasswordBearer`) |
| Access 30 мин + refresh 365 дней, sliding-окно | `core/auth.py:35`, `:108` |
| Сессия живёт в БД, `logout` её инвалидирует | `models/user_session.py`, `routers/auth.py:521` |
| Логин уже принимает `device_info` и `user_agent` | `routers/auth.py:283` |
| Вход по email **или** телефону | `core/auth.py:153` |

Мобильный клиент впишется в этот контракт без изменений: токен передаётся в заголовке, поле для устройства предусмотрено, refresh-логика (молчаливое продление при 401) уже написана на фронте и переносима по смыслу.

### 2.2 Права режет сервер

17 permission-кодов автосервиса (`utils/autoservice_access.py:22`), каждый эндпоинт проходит через `require_autoservice_permission` / `require_any_autoservice_permission` (`:74`, `:84`), статус сотрудника — через `require_autoservice_staff` (`:142`).

Следствие: для роли «автосервис» в приложении **не нужен новый API-скоуп**. Те же эндпоинты, те же права; в приложении просто не показываем разделы, которые на телефон не едут.

### 2.3 контракты API машиночитаемы

30+ автосервис-роутеров под единым префиксом `/api` (`routers/__init__.py:95`), ответы почти везде через Pydantic `response_model`. FastAPI отдаёт `/openapi.json` → типизированный клиент можно генерировать, а не переписывать руками сотни вызовов.

### 2.4 Уведомления уже абстрагированы

Единая точка `notification_service.dispatch_user_notification(event_type, push_data, email_*)`, предпочтения каналов в `User.notification_prefs` (JSONB) + легаси-флаги `notify_push_enabled` / `notify_email_enabled`. Добавление канала «нативный push» — одна ветка в диспетчере, а не переписывание рассылок.

### 2.5 Экспорт отчётов — серверный

`/autoservice/reports/payroll.xlsx`, `order-economics.xlsx`, `warehouse-stock.xlsx`, `rossko-sales.xlsx`, `/autoservice/finance/receipts.xlsx` — отдают bytes, авторизация Bearer. В приложении это решается скачиванием + системным «Поделиться», переписывания не требует.

### 2.6 Долгие операции уже уходят в Celery

`autoservice_notification_tasks`, `autoservice_caldav_tasks`, `sync_calendar_to_bookings.delay(...)` с возвратом `task_id`. Механизм есть, но см. п. 3.7 — общего эндпоинта статуса задачи нет.

## 3. Блокеры: что нужно сделать на бэкенде

Отранжировано по боли. Номера соответствуют плану в разделе 6.

### 3.1 `sub` в токене — это email  【 Blocker 】【 Средняя цена 】

`get_current_user` читает `payload["sub"]` и ищет пользователя `get_user_by_email` (`core/auth.py:180`).

Клиентский аккаунт сегодня создаёт **сотрудник**, и он требует email: без него — 400 «Укажите email клиента перед созданием аккаунта» (`routers/autoservice_clients.py:659`). Реальных клиентов с email у автосервиса меньшинство.

Нужно: `sub = user_id` (или новый claim `uid`) во всех местах проверки — `get_current_user`, `refresh_auth_tokens`, WebSocket (`routers/websocket.py:283`). Это правка, задевающая все проверки сессий, поэтому делать её надо первой и с тестами.

### 3.2 Нет входа по SMS-коду  【 Blocker 】

Вход только по паролю. Для клиента в приложении это неприемлемо: пароль из письма, который выдал сотрудник, пользователь не помнит и менять его не будет.

Нужно: `POST /auth/otp/request` + `POST /auth/otp/verify` (выдаёт ту же пару токенов), модель кода с TTL и числом попыток, троттлинг отправки, выборка клиента по нормализованному телефону. Плюс шлюз SMS уже есть и переключается в админке (`site_settings.sms_provider`, `smsgold`/`smsc`) — инфраструктура отправки на месте, нет только кодов.

### 3.3 Опасная логика: склейка клиентов по хвосту телефона  【 Blocker / Безопасность 】

`related_autoservice_client_ids(include_phone_matches=True)` (`utils/autoservice_access.py:266`) берёт **всех** клиентов организации и добавляет в «свои» тех, у кого совпадают последние 10 цифр номера.

Для сотрудника это feature (человек с двумя карточками видит обе). Если клиентский скоуп пройти через ту же функцию — при опечатке в номере клиент получит чужие заказ-наряды, суммы и ПДн. Требование: клиентские эндпоинты работают **только** по `user_id`, `include_phone_matches=False`, и это надо закрепить тестом на утечку, а не «договориться».

Сейчас единственная готовая клиентская выборка — `/autoservice/inspection-bookings/me` (`routers/autoservice_inspections.py:182`), и она уже вызывает `related_autoservice_client_ids(..., include_phone_matches=False)` — то есть правильный образец в коде есть, его надо растиражировать, а не изобретать.

### 3.4 Нет клиентского слоя данных  【 Blocker 】

Есть записи на осмотр (`.../me`), есть «гараж» (`autoservice_garage`), но «мои заказ-наряды», «история ремонтов», «мой статус / дебет» в клиентском скоупе не покрыты — все эти эндпоинты требуют permission и `require_autoservice_staff`.

Нужен компактный слой вида `/api/me/autoservice/...`: мои авто, мои записи, мои заказ-наряды (только поля, уместные клиенту), история визитов. Плюс серверный `grand_total` отдавать уже готовым числом, а не заставлять клиента считать экономику.

### 3.5 Пагинация есть ровно у одного списка  【 High 】

`GET /autoservice/repair-orders` (`routers/autoservice_repair_orders.py:1616`) — `limit` 1..200, `offset`, ответ `RepairOrderListPage` с `total`. Всё остальное: `list[...]` без лимита — `/autoservice/clients` (`:475`), `warehouse/items` (`:362`), `warehouse/receipts` (`:681`), `warehouse/expenses` (`:1045`), `inspection-bookings` (`:286`).

Дополнительно: при активном фильтре «Оплата» бэкенд выбирает весь набор в Python и режет страницу в памяти (`:1737`). На десктопе не видно, на телефоне — трафик, батарея и время первого экрана.

Нужно: `limit/offset` (курсор лучше) на всех списочных эндпоинтах, которые попадут в приложение, и ответить для себя, что делать с фильтром оплаты при росте числа заказов.

### 3.6 Печатные формы не существуют вне браузера  【 High 】

`RepairOrderPrintPage.jsx`, `RepairOrderInvoicePrintPage.jsx`, `RepairOrderPaymentReceiptPrintPage.jsx`, `RepairOrderUpdPrintPage.jsx` — это React-страницы под `window.print()`. В приложении их открыть нечем.

Нужно: серверная генерация PDF (заказ-наряд, счёт, УПД, акт) + эндпоинт, отдающий bytes, и тогда в приложении это «скачать и поделиться» / «открыть предпросмотр». Это ровно та работа, которой нет в текущем покрытии, а она обязательна для сценария «клиент подписал / получил документ».

### 3.7 Долгие задачи: статус не опросить  【 Medium 】

`sync-from-calendar` возвращает `{task_id, message}` (`routers/autoservice_caldav.py:114`), но универсального `GET /tasks/{id}` нет. Для «импорт из покупок на склад», «реконсил Drom», «обработка фото» приложению нечем показать прогресс и нечем отличить «ещё идёт» от «упало».

### 3.8 Push — только web push  【 Blocker для фичи напоминаний 】

Канал реализован через VAPID + pywebpush и таблицу `PushSubscription` (`routers/notifications.py`). Для iOS/Android он бесполезен: нужен FCM + APNs, токен устройства, привязка к пользователю, переживание смены токена, обработка tap→deep link.

Объём: новая таблица (или колонка) device tokens, эндпоинт регистрации, транспорт в `dispatch_user_notification`, ключи Firebase в `.env` (не в репозиторий). Напоминания об осмотре (за 15 мин, за час, накануне 20:00) уже живут в CalDAV-логике — в приложении они должны идти по тому же расписанию, но через push.

### 3.9 Даты — naive wall-clock Europe/Moscow  【 High 】

Метки статусов и даты пишутся `datetime.now()` (locale МСК), колонки создавались schema-патчами как TIMESTAMPTZ, из-за чего в коде уже есть `_normalize_dt` перед любым сравнением. В браузере пользователь не видит ошибки; на телефоне с другим TZ (Екб, Дубай) даты уедут.

Нужно выбрать правило и не нарушать его: либо отдавать ISO с offset, либо явно «все даты — МСК без offset» и зафиксировать константу/парсер на клиенте. Второе дешевле, первое честнее.

### 3.10 Относительные URL файлов  【 Medium 】

Раздача смонтирована как `/uploads`, `/pictures`, `/videos`, `/vehicle_pictures`, `/media/{path}` (`main.py:978`–`:1049`), а в ответах API лежат относительные пути. В вебе их доклеивает домен, приложению нужен абсолютный URL. Правится централизованно (один хелпер на отдаче), но если не сделать — вылезет в десяти экранах как «не грузится фото».

### 3.11 Мелочи, которые укусят позже  【 Low 】

- `cleanup_old_user_sessions`: максимум 5 сессий на пользователя **с одного IP** (`core/auth.py:233`). Под операторским NAT/CGNAT у мобильных абонентов десятки клиентов с одного IP.
- IP-рейт-литы (`middleware/rate_limit_middleware.py`, `utils/rate_limit.py`) — при общем IP на целый город дают периодические 403/429, которые выглядят как баг приложения. Проверить лимиты до релиза.
- Смена прав сотруднику инвалидирует его активные сессии (`routers/employees.py:244`) → приложение выбрасывает в логин. Нужен мягкий UX-обход, а не «так и задумано».
- CORS через настройки: нативные запросы не шлют `Origin`, но убедись, что nothing в middleware не проверяет его как признак «своего» клиента.

## 4. Готовность структуры проекта (фронтенд)

| Метрика | Значение |
|---|---|
| js/jsx-файлов в `src` | 710 |
| Отдельных `*MobileView.jsx` | **4** |
| Файлов с ветвлением `isMobile` / `max-lg:` | 42 |
| Страниц автосервиса | 27 (из них 8 — тесты и печатные формы) |

Вывод: «мобильная версия» сейчас — это адаптивная разметка тех же десктопных страниц, а не продукт. Напрямую в приложение она не переносится.

**Что переносится хорошо (главная ценность):**
- Redux slices — транспортно-независимы, уходят почти 1:1 (соглашение проекта: все API-запросы живут в слайсах).
- Чистые хелперы и логика планировщика: `autoservicePlannerLayout.js` (`assignPlannerLanes`, `plannerItemBarColor`, `plannerInspectionSegment`), `warehouseListUi.js`, `autoserviceOrderZoneFilter.js`, `repairOrderFormDraft.js`. Они уже покрыты тестами — это готовый переносимый слой.
- Дизайн-токены Tailwind (`brand`, `success`, `danger`) → тема NativeWind.

**Что не переносится ни при каком стеке (делать заново):**
- service worker / precache, react-router 7, `import.meta.env`.
- `localStorage`/`sessionStorage`: фильтры страниц (`usePersistedPageFilters`), режим планировщика, **и черновики заказ-нарядов** — это осознанно переносимое поведение, а не побочный эффект; черновик создания привязан к токену в sessionStorage (`sg:repair-order-form:create:<token>`).
- `document.cookie`, прямой DOM, `window.print()`, скролл-прижатие шапки планировщика через JS-зонды (`--sg-planner-head-shift`).
- Компактные десктопные таблицы (`py-2`, `text-xs`, `table-fixed`) — на телефоне они не «уменьшенные», а другие по структуре; эталон десктопных таблиц в приложение не едет.

**Отдельно про окружение разработки:** репозиторий лежит в OneDrive (`Рабочий стол\autoparts`). Синхронизация OneDrive по `node_modules`, Gradle- и Xcode-артефактам мобильного проекта даёт бесконечные конфликты и медленные сборки. Мобильный проект держать вне OneDrive, в идеале — отдельный репозиторий, а источником правды сделать OpenAPI-контракт.

## 5. Стек: чем писать

### Рекомендация: React Native + Expo (managed workflow) + EAS Build

Это единственный вариант, закрывающий сразу три твоих условия:

1. **Полная разработка на Windows.** Android-эмулятор и живой Android, hot reload, отладка — на Windows. Android Studio у тебя уже стоит.
2. **iOS без Mac в ежедневном цикле.** На iPhone экраны отлаживаются с Windows по сети — Expo Go или development build. Mac нужен **только** в момент сборки подписанного `.ipa`, и твой готовый Mac (Air 2017) для этого не годится: он стоит на потолке macOS 12 Monterey, то есть максимум Xcode 14.2, что не проходит ни современные тулчейны, ни требования App Store. Остаётся облачная сборка (EAS) — но она, как и TestFlight, APNs и universal links, упирается в платную подписку Apple Developer. Пока подписки нет, iOS-ветка существует только как «проверено в Expo Go».
3. **Переиспользование того, что уже стоит денег:** Redux slices, логика планировщика, тесты на хелперы, токены темы, OpenAPI-контракт.

Компоненты/библиотеки под твои экраны: Expo Router или react-navigation; TanStack Query **или** перенос текущих Redux slices; NativeWind v4 для токенов; FlashList вместо таблиц; кастомная недельная сетка поверх перенесённой `autoservicePlannerLayout` (это чистая JS-логика — сильный аргумент именно в пользу RN); expo-image-picker + твоё же сжатие; expo-notifications → FCM/APNs; expo-print / share для PDF; Sentry с отдельным release tag и source maps.

### Почему не альтернативы

- **Capacitor** (обёртка текущего мобильного веба) — до двух сторов в ~2 раза быстрее, но «полноценная роль автосервиса» упирается в WebView: клавиатура над формами, safe-area, виртуализация больших списков, жесты, память на планировщике, и риск отказа App Store по пункту 4.2 («сайт в обёртке»). Поскольку текущая моб вёрстка — адаптив десктопа, а не мобильный UX, «быстро» там только на первом этапе. Подходит как прототип, не как целевой продукт.
- **Flutter / нативные Swift+Kotlin** — качество максимум, но JS-слой не переезжает вообще: ни Redux, ни хелперы планировщика, ни тесты. При том, что вся твоя бизнес-логика живёт в JS и Python, это самая дорогая опция.
- **PWA без сторов** — отпадает: iOS push и «установленность» ограничены, офлайн и нативные возможности нет.

### Архитектура доставки

- Приложение живёт в этом же репозитории, каталог `mobile/app` — общее CI и один источник правды по API.
  OneDrive при этом остаётся минусом: для `node_modules`, `.expo`, `ios/build` и `android/app/build`
  нужны исключения синхронизации, и настраиваются они на этапе 2.
- Контракт = OpenAPI с бэкенда, клиент генерируется.
- **Правило обратной совместимости важнее версионирования:** приложение лежит у пользователя неделями, сервер обновляется сегодня. Для мобильных эндпоинтов — additive-only: поле/колонку можно добавить, переименовать или убрать — только с новой версией. В заголовки `X-App-Version` и логировать его, чтобы видеть, сколько старых версий ещё в бою.

## 6. План работ и оценка

> Первичная прикидка, оставлена как обоснование объёма. Рабочая карта — `mobile/docs/PLAN.md`, 21 этап;
> там же учтены ответы из раздела 8 (без сторов, офлайн-чтение, пилот на проде), из-за чего объём
> бэкенд-подготовки вырос, а OTP, `sub` → `user_id` и `/api/me/*` уехали во вторую очередь с ролью
> «клиент». Нумерация «0.x» в этой таблице и «0.x» в `decisions.md` — разные вещи.

### Этап 0 — бэкенд-подготовка (≈1.5–2 недели, почти вся «неготовность»)

| # | Работа | Priority |
|---|---|---|
| 0.1 | `sub` → `user_id` во всех проверках (включая WebSocket) + тесты | Blocker |
| 0.2 | OTP-вход по телефону (запрос/подтверждение/троттлинг) на существующем SMS-шлюзе | Blocker |
| 0.3 | Клиентский слой `/api/me/autoservice/*` строго по `user_id`, без fuzzy-склейки; тест на утечку | Blocker |
| 0.4 | FCM/APNs-канал: device tokens, регистрация, ветка в диспетчере, deep link при тапе | Blocker |
| 0.5 | Пагинация на всех списочных эндпоинтах, которые попадут в приложение | High |
| 0.6 | Серверный PDF печатных форм (заказ-наряд, счёт, УПД, акт) | High |
| 0.7 | Фиксация правила по таймзонам + absolute media URLs | High |
| 0.8 | Опрос статуса Celery-задачи | Medium |

### Этап 1 — каркас приложения (≈1–2 недели)

Expo-проект, вход (пароль + OTP), хранение токенов и молчаливый refresh, роутер, тема из токенов Tailwind, API-клиент из OpenAPI, EAS preview-сборки (Android APK из Windows, iOS — на iPhone), Sentry, сборка в CI.

### Этап 2 — роль «автосервис» (≈6–10 недель, по разделам)

Порядок по ценности, а не по удобству кода:

1. «Сегодня» / дашборд (`/autoservice/dashboard/summary` — один запрос, уже разложен по правам)
2. Записи на осмотр (список, подтверждение, создание)
3. **Заказ-наряды** — карточка, затем форма создания. Самый дорогой экран: форма у вас объёмная (позиции, работы, подрядчики, скидка, НДС, импорт из покупок и корзины, черновики)
4. Планировщик (перенос `autoservicePlannerLayout` + недельная сетка + зелёный сегмент осмотра)
5. Склад (остатки, приход, расход, возврат)
6. Финансы и отчёты — только просмотр + экспорт в Excel
7. Клиенты, сотрудники, подрядчики, организации
8. Настройки — read-only

### Этап 3 — роль «клиент» (≈2–3 недели, только после этапа 0)

Вход по телефону → мои авто → запись на осмотр → статус и история заказ-нарядов → профиль → (позже) чат. Чат частично готов: WebSocket-эндпоинт уже есть и принимает Bearer-токен в query-параметре.

### Ориентир по срокам

- MVP для двух сторов (дашборд + записи + заказ-наряды + клиенты + push): **6–8 недель**.
- Полное покрытие роли «автосервис», как описано: **3–4 месяца**.

Не переносится в приложение осознанно: админка, SEO/moderation, Avito- и Drom-интеграции, бэкапы, настройки наценки, VPN-бот, всё «на однуorganization-галку».

## 7. Риски, которые надо принять заранее

1. **App Store 4.2.** Если приложение — обёртка сайта, отказ вероятен. Нативные фичи (push, deep links, камера, предпросмотр PDF, офлайн) — не «приятно», а условие публикации.
2. **Публикация для B2B-аудитории.** У тебя мульти-тенант: приложение пойдёт в публичные сторы, а не «внутренний Tool» — значит требования Apple и Play полные, включая приватность (Privacy Policy, декларация сбора данных, согласия на push) и восстановление покупки/аккаунта.
3. **Разрыв версий.** Приложение у пользователя живёт неделями. Без аддитивного правила и заголовка версии один рефакторинг эндпоинта ломает старых клиентов молча.
4. **Два продукта на одном бэкенде.** Любая правка бизнес-логики теперь проверяется в двух UI. Соглашение про «эталон таблиц» и общие хелперы (`warehouseListUi`) в приложении работать не будет — там своя система.
5. **Разработка на Windows + iOS-релизы** требуют либо Mac как build-хост, либо облачных сборок (EAS) — и то и другое добавляет внешний зависимости от чужого uptime/квоты.

## 8. Что решить до первой строки кода — решено 06.11.2026

Полный список зафиксированных ответов: `mobile/docs/decisions.md`; работы по ним разложены по 21 этапу в
`mobile/docs/PLAN.md` (этот отчёт остаётся обоснованием, план — карта).

1. **Вход клиента:** в v1 клиента как отдельной роли в приложении нет вовсе — сначала роль «автосервис» со
   входом **email + пароль** (в том же поле работает телефон), как на сайте. OTP, `sub` → `user_id` и отказ
   от fuzzy-склейки по хвосту телефона (п. 3.1–3.3) переносятся во вторую очередь вместе с ролью «клиент».
2. **Офлайн:** нужен по максимуму — чтение без сети во всех разделах роли «автосервис», запись только
   онлайн. Слой кэша, таблица протухания и маркировка возраста данных проектируются сразу (этап 3), а не
   прикручиваются потом.
3. **Печатные формы:** серверный PDF единый для веба и приложения (п. 3.6 → этап 1.5). Веб-страницы печати
   постепенно уходят, отдельной мобильной реализации не будет.
4. **Границы приложения:** полное покрытие роли «автосервис», включая полную форму заказ-наряда. Массовые
   правки справочников, этикетки/термопринтер, Avito/Drom, SEO и модерация остаются на сайте; ссылка на
   веб — легитимный ответ для экрана, который неудобно делать пальцем.
5. **Публикация:** аккаунтов нет и не покупаем — в v1 нет ни Play Console, ни Apple Developer. Android
   расходится APK по ссылке с сервера с экраном «есть обновление», iOS до появления подписки или железа
   проверяется только через Expo Go. Пункт 2 раздела «Риски» (полные требования стор) поэтому в v1 не
   действует — но он возвращается целиком вместе с этапом публикации.
6. **Пилот:** свой автосервис, свои сотрудники, рабочие прод-данные. Отсюда три обязательных правила на
   всех этапах: аддитивный контракт без изменения дефолтов, бэкап перед включением write-экранов и
   обкатка каждого экрана сначала в read-only.
